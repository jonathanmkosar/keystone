# P15-01. The admin account

Status: done
Lane: core
Depends on: P2-02, P2-04, P2-05
Owner gate: None: A1 and A2 are answered.
Built without the gate: Everything.
Scope: Admin accounts in their own database, `data/admin/admin.db`: accounts, passwords and passkeys, sessions with `ksa_` tokens, and the admin audit log. `tools/admin add` and `password`, `/admin/sign-in`, the session and idle limits, and a door that tells a person's token from an admin's before anything is read. Remove the first pass's mark, `tools/tenant admin` and the step-up. Keep `internal/adminview` and the two audit logs, and show a person the admin entries of their own log in their Settings. A decision record replaces 0640 and 0643.
Proof: A person's token is refused on every admin route and an admin's on every person's route. An admin account has no chat, file or model route. Every admin call is in both audit logs, and the person sees it.

See `docs/plan/SPEC-router-and-admin.md`, Part 2, "The admin account" and "What an admin never sees", for the design this item delivers; `docs/plan/PLAN.md` for the intent; and `docs/plan/PARALLEL.md` for lanes and gates.

## Plan

The first pass, on branch `core/p15-01-admin-mark` (merged), built an admin mark on a person in `keystone.json`, `tools/tenant admin`, a step-up and the admin door (decisions 0640 to 0646, journal `core-015`). This pass, on `core/p15-01-admin-account`, reworks it into a separate admin account, as the owner answered A1 and A2 on November 27, 2026.

- **The admin database.** A new package, `internal/adminaccount`, owns `data/admin/admin.db` with migrations of its own: accounts (id, name, added), one password each, passkeys, prompts, sessions and the admin audit log (the shape of a person's, append-only by triggers). A session's token is `ksa_` and 32 random bytes as hex, kept only as a hash. A session lasts `admin.session_for` (8h) and ends after `admin.idle_for` (30m) without use; both are install settings in `settings/core.json`. Passwords and passkeys follow a person's rules: the same hashing, count of wrong tries and wait (the `signin.` settings), through small exported helpers in a new file in `internal/signin`. Not encrypted at rest: it holds no person's data (P15-06 covers people).
- **`tools/admin`.** `add "Name"`, `password <id>` (from standard input), `list`, and `remove <id>`, which refuses the last account without `--yes`. No route makes or removes an account.
- **The door.** The API shell picks the token by its form before anything is read: on a path under `/api/v1/admin/` the admin cookie (`keystone_admin`, path `/api/v1/admin/`), elsewhere the person's. A `ksa_` token goes to the admin side: its session is checked in `admin.db`, the call is written in the admin audit log before and after, and a person's route is refused (403 `admin_account`). A person's token on an admin path stays on the person's side, is recorded in their own log and refused (403 `not_admin`). `api.Call` carries the admin's session and the admin database on an admin route, and no tenant store.
- **Routes (contract first).** Doors: `POST /api/v1/admin/session` (password or passkey) and `POST /api/v1/admin/session/passkey` (a prompt). Admin: `GET` and `DELETE /api/v1/admin/session`, `GET /api/v1/admin/people` (id, name, added, last sign-in), and the admin's own passkeys (list, a prompt to add, add, remove). For a person: `GET /api/v1/audit/admin`, the admin entries of their own log. The OpenAPI document regenerated.
- **`internal/adminview`** stays the only way to a person: it checks the admin account exists in `admin.db`, writes the person's log first with the actor `admin:<account id>` and the account's name, and returns numbers and settings. The admin cannot read a person's log.
- **Removed.** The mark (`Tenant.Admin`, `Install.SetAdmin`, `IsAdmin`, `Marks`, the save that merged marks, the backup lines), `tools/tenant admin`, the step-up (`signin.StepUp` and its passkey pair, `Session.AdminUntil`, the routes, `admin.step_up_for`, the `StepUp` route mark). A forward migration drops `admin_until` and the `step-up` prompt purpose; the two step-up migrations stay as they ran. An old `keystone.json` with `admin` still loads, and the next save drops it.
- **Screens.** `/admin/sign-in` and a bare admin page (who, sign out; the admin screens are P15-02 to P15-04), and Settings, Admin access, for a person.
- **The check `admin isolation`**, at least as strict: the imports (adminview, adminapi and adminaccount reach no package with a person's content; adminapi does not import `internal/tenant`; adminview and adminapi never list an audit log); accounts made and removed from `tools/admin` alone; no mark on `tenant.Tenant`; no admin route's path names chats, messages, files, uploads, artifacts, models, memory or projects; and a walk with the real handler: a person's token refused on every admin route and recorded in their own log alone, an admin's refused on every person's route and recorded in the admin log alone, every admin route in the admin log, the people read in both logs and seen by the person, a signed-out or removed account refused at once, and no `ksa_` token in any body or the server's log.
- **Write-up.** A decision record replacing 0640 and 0643 (both marked superseded), others after it, `admin.md`, `signin.md`, and the journal `core-016`.

## Result

First pass (November 27, 2026; decisions 0640 to 0646, journal `core-015`): an admin mark on a person and a step-up, on the assumed A1 and A2. Replaced the same day, when the owner answered.

Second pass, built as planned on November 27, 2026; see `docs/architecture/admin.md`, decisions 0650 to 0655 and the journal `docs/journal/2026-11-27-core-016.md`. An admin is a separate account in `data/admin/admin.db` (`internal/adminaccount`), made by `go run ./tools/admin`, signing in at `/admin/sign-in` with a `ksa_` token in its own cookie for `admin.session_for` and no longer than `admin.idle_for` unused. The shell tells the two tokens apart by their form: a person's is refused on every admin route (403 `not_admin`, in their own log) and an admin's on every person's route (403 `admin_account`, in the admin log). Every admin call is in the admin audit log, every read of a person also in theirs with the admin's name, and the person sees it in Settings → Admin access (`GET /api/v1/audit/admin`). The mark, `tools/tenant admin` and the step-up are removed, with a forward migration. The `admin isolation` check holds the new shape in both directions. Two choices beyond the plan: sign-in takes the account's name or id, and the admin's passkeys have routes of their own (list, prompt, add, remove), behind `signin.passkeys`. The two screens have no mockup and are provisional; the admin screens for people, the install and settings are P15-02 to P15-04.
