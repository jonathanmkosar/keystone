# P12-02. Gmail and Calendar connectors

Status: provisional
Lane: agents
Depends on: P7-04
Owner gate: Jonathan signs in to Google for the connectors.
Built without the gate: Built and tested against a stand-in Gmail and Calendar server.
Scope: Gmail and Google Calendar as connectors, with sends and guest-notifying changes behind approval cards.
Proof: Drafting and sending an email needs approval; personal calendar changes follow the policy.

See `docs/plan/PLAN.md` for the design this item delivers, and `docs/plan/PARALLEL.md` for lanes and gates.

## Plan and result

Plan, November 25, 2026 (agents, branch `agents/p12-02-gmail-calendar`):

- **Built-in connectors, in process.** Gmail and Google Calendar are connectors of P7-04's kind with a third transport, `google`: two rows in the person's `connectors` table, named `gmail` and `calendar`, sharing one Google sign-in. Their tools are Go functions behind the same pool, `ForCall`, `load_tools`, chat switches, policies and audit path as every connector tool, not an MCP server Keystone runs itself: one less process and protocol, and the approval card and the "reaches other people" flag come straight from Go (a decision). A migration widens the transport check and adds `google_accounts` (the connected address and granted scopes) and `google_pending` (a started sign-in's state and PKCE verifier, ten minutes, used once).
- **`internal/google`**, a new package: the OAuth 2.0 client (authorization address with PKCE S256, `access_type=offline`, the code exchange, refresh, revoke), and the Gmail and Calendar REST calls and tool definitions as plain data and functions. Narrowest scopes: `gmail.readonly` and `gmail.compose`, `calendar.events.owned`, and `openid email` to name the account. `internal/google/googletest` is a stand-in Google (token, revoke, Gmail and Calendar endpoints) with invented data, for tests and `verify` only.
- **Tokens.** The refresh token in the person's vault (`connector.google`), never in settings, logs, results, events or the audit log; access tokens in the pool's memory, refreshed in `reachFor` (the one place a token is read) a minute before they expire; everything a Google endpoint sends back has the refresh token, the access token and the client secret taken out. The OAuth client id is a tenant-admin setting (`agents.google_client_id`, empty until the owner sets it) and the client secret is stored by the admin in the person's vault (`google.client_secret`); until both exist the connectors show "not set up" with what is needed. Every Google address is a setting and is dialled as web_fetch dials: public addresses only, no proxy, no redirect.
- **Sign-in.** A same-origin redirect: "Connect Google" asks the server for the authorization address (the redirect is the page's own origin plus `/settings/connectors/google`, or `agents.google_redirect_url` when set); Google sends the browser back to that page, which posts the code and state to the server. The session cookie is SameSite=Strict, so the callback is a page and not an API route, and no door route is added. Routes: `GET /api/v1/google`, `POST /api/v1/google/start`, `POST /api/v1/google/finish`, `DELETE /api/v1/google`.
- **Tools.** Gmail: `search` and `read` (read only, outside content), `draft` (changes something: asks by default), `send` (always asks, whatever the policy). Calendar: `list_events` and `get_event` (read only, outside content), `create_event`, `update_event`, `delete_event` (ask by default on the person's own calendar), and any of them that invites, updates or tells guests always asks. An update or delete names the event's current title and guests, and the call checks them against the live event before it changes anything, so the card can never show fewer people than are reached. Each card says exactly what will be sent or changed: recipients, subject and a body excerpt; event title, time and guests.
- **The rule.** `approval.Call` gains `Others` (the call reaches other people) and `ReasonOthers`: such a call asks under `always` and `ask`, and `never` still refuses. `tools.Tool` gains `ReachesOthers(input)`, which the turn passes to `Decide`, and `tools.Run` refuses a standing approval for a call that reaches others, so the rule holds twice. A scheduled or background run that wants to send waits for the card like any turn. Lines in `internal/turn/approvals.go` (the `Decide` call and the card's sentence) and `policies.go`/`connectors.go` (a flag on the approvals screen).
- **The screens.** Settings → Connectors gains a Google section: not set up (and what is needed), Connect Google (Gmail, Calendar), connected as an address, Disconnect. The Approvals screen marks a tool whose calls can reach other people.
- **Proof**, with the stand-in on this machine: drafting and sending an email asks and runs once approved; a send set to always still asks; a personal calendar change follows the person's policy (always runs, ask asks); a guest-notifying change always asks; an update that leaves out an event's guests is refused and changes nothing; tokens appear in no result, event, audit entry, kept problem or file (a surface of `no keys in output`); a step of `calls recorded` runs the test tenant's recorded Google turns on the real server; the `approval` check covers `Others`. Real Google is never called.

Left out: attachments, labels and archiving, replying to a thread by id beyond In-Reply-To, calendars the person does not own, recurring-event edits beyond one occurrence, push notifications, and choosing per call whether guests get an email.

### Result

Provisional on November 25, 2026, on the owner gate: everything in the scope is built and the proof passes against a stand-in Google on this machine; real Google waits on the owner making an OAuth client and signing in (`docs/runbooks/google.md`). The screens wait on the agent mockups (P1-05).

- **Gmail and Calendar as connectors.** Two built-in connectors, `gmail` and `calendar`, with the transport `google`, run in process behind P7-04's registry, pool, switches, policies, `load_tools` and audit path (decision 0350). Nine tools: `gmail_search`, `gmail_read`, `gmail_draft`, `gmail_send`, `calendar_list_events`, `calendar_get_event`, `calendar_create_event`, `calendar_update_event`, `calendar_delete_event`. Results are outside content.
- **Sends and guest-notifying changes behind approval cards.** A call that reaches other people always asks, whatever the policy, and only the person's own answer runs it, held twice: in `approval.Decide` (`Others`, the reason `others`) and in `tools.Run` (`CheckReach`) (decision 0351). A change to an event names its title and guests and is checked against the live event, so a card never shows fewer people than are reached (decision 0353). Each card says exactly what is sent or changed.
- **The sign-in.** OAuth 2.0 with PKCE, returning to a page on the same origin, the narrowest scopes, the refresh token in the person's vault and access tokens in memory, refreshed in `reachFor`; the OAuth client is the owner's, a tenant-admin setting and a vault entry, and until both exist the screen says what is missing (decision 0352). Four routes under `/api/v1/google`.
- **The proof**, in `go test ./internal/turn` and a step of `verify`'s `calls recorded`: drafting and sending an email asks and runs once approved; a send set to always still asks; a personal calendar change asks at its default and runs set to always; a change that invites a guest always asks; an update that leaves out an event's guests changes nothing; no token in any event, answer or audit entry. `approval` checks the rule; `no keys in output` has a Google surface. `verify` is 22 of 22.
- One migration, `20261125T190000_google_connectors.sql`; ten settings; `docs/api/openapi.json` regenerated. The doc is `docs/architecture/google.md`; decisions 0350 to 0353; the runbook `docs/runbooks/google.md`; the journal is agents 007. Seen in a browser on port 7993 as the test tenant, with the stand-in on port 7994.
