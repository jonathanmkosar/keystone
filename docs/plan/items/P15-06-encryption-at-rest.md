# P15-06. Encryption at rest

Status: doing (core)
Lane: core
Depends on: P2-01, P2-03
Owner gate: None.
Built without the gate: Everything.
Scope: Each person's database (with its write-ahead log and temporary files), uploads, files, artifacts and project files encrypted with the person's data key under the install master key. Choose how the database is encrypted and record it in a decision record. Files sealed in chunks with AES-256-GCM, bound to the tenant id, named by a keyed hash. Encrypt an existing install in place at first start, one person at a time after a backup. Touches the chats lane's uploads and the agents lane's artifacts: say so in the journal.
Proof: Every file in a person's folder, read from disk, holds no marker word and no plain database header. A folder copied to another tenant, or opened without the master key, does not open. An interrupted first start resumes and never opens a half-done person. The load test and `verify` pass with encryption on.

See `docs/plan/SPEC-router-and-admin.md`, Part 2, "Encryption at rest", for the design this item delivers; `docs/plan/PLAN.md` for the intent; and `docs/plan/PARALLEL.md` for lanes and gates.

## Plan

Branch `core/p15-06-encryption-at-rest`, cut from `reboot`.

- **The keys.** The person's data key (decision 0006) never leaves `internal/secrets`: a new `Vault.Subkey(purpose)` gives a key derived from it with HKDF-SHA-256, bound to the tenant id, and makes the data key first if the person has none. From that one subkey a new package, `internal/atrest`, derives the database key, the files key and the names key.
- **The database.** Encrypted page by page through a SQLite VFS written in Go and registered with the driver Keystone already uses (`modernc.org/sqlite/vfs.Register`, in v1.63.0): no cgo, no new module, Waymarks' driver kept. Every file SQLite opens by name, the database and its journal, goes through it, sealed in 4096-byte blocks with AES-256-GCM, each bound to the tenant id and to its place in the file; temporary files never reach the disk (the driver keeps them in memory). That VFS has no shared memory, so a sealed database uses a rollback journal (`journal_mode=truncate`, `synchronous=full`) instead of the write-ahead log; the driver keeps the connections of one process apart, and a lock on the file keeps a second process out while the first has the person open, waiting up to `encryption.lock_wait`. The options weighed (this VFS; another pure-Go driver with an encrypting VFS of its own; sealing the whole file; SQLCipher, which needs cgo) and what each costs Waymarks parity and backup and restore go in a decision record, with the load test's numbers.
- **Files.** Uploads, project files and artifacts are written and read through a new `Store.FilesFolder()` and `Store.ArtifactsFolder()`, which seal a file in 64 KiB chunks with AES-256-GCM under a key of its own, bound to the tenant id, and name each part of a path by a keyed hash (HMAC-SHA-256), so equal files do not have equal names across people. For a plain tenant they pass straight through. The chats lane's `uploads` and `chat`, the projects lane's blobs and the agents lane's `artifacts` change only at the lines that write, read, stat, rename and remove those files.
- **A sealed folder** holds `seal.json` (format, tenant id, a key check), the sealed database, `secrets.bin` and the sealed files. A folder without it is plain and opens as today.
- **First start.** With `encryption.at_rest` on (the default), the server seals every plain person at start, one at a time, before it serves: (1) a backup of the person in the P13-04 format, under a random passphrase that the install master key wraps beside it; (2) a sealed copy built in `tenants/.<id>.sealing/`; (3) read back: the database opened through the VFS, checked by SQLite and counted table by table against the plain one, every file opened and compared by hash, everything synced, and `seal.json` written last; (4) the plain folder renamed aside and the sealed one into place; (5) only then the plain folder removed. A start cut short at any step finds the leftovers and finishes or starts that person again: a folder in place is either the whole plain one or the whole sealed one. A failure leaves that person plain and untouched, stops the run and is reported; the server still starts. A new person is made sealed.
- **Backup and restore** (P13-04): a sealed person's backup carries the sealed database and files, with the data key re-wrapped as today; a restore into a sealing install seals a plain backup before it is put in place.
- **Settings** in `settings/core.json`: `encryption.at_rest` (bool, true, install) and `encryption.lock_wait` (duration, 30s, install).
- **Proof.** Tests in `internal/atrest` and `internal/tenant`: every file in a sealed person's folder, read from disk, holds no marker word and no SQLite header; the folder copied into another person's, or opened with another master key, does not open; a first start cut at each step resumes and never opens a half-done person; a torn journal block reads as SQLite expects. A standing check, `encryption at rest`, runs the real packages (chat, uploads, artifacts, project files, memory) on a sealed install and scans the folder. The load test runs with encryption on, and `verify` passes.
- **Left out.** Rotating a data key; sealing the agent's browser profile while its browser runs (it is removed at close); turning a sealed install back to plain.
