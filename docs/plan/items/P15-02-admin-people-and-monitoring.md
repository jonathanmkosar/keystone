# P15-02. People, the install and monitoring

Status: provisional
Lane: core + interface
Depends on: P15-01
Owner gate: None for the server side. The screens follow the approved drafts.
Built without the gate: Everything.
Scope: The people, one person's usage and the whole install's routes; adding a person with a setup code and `/setup`; disabling and enabling a person; Operations split, with the person's own under Settings and install-wide parts only in the admin account (a decision record changes 0460); and the admin screens People, A person and Install.
Proof: The numbers equal each person's own Usage and Operations figures, and the install's equal their sum. A disabled person cannot sign in, their sessions end, their schedules do not run and their share links answer as revoked; enabling restores it. A setup code works once and not after it expires. No content of a person reaches a reply.

See `docs/plan/SPEC-router-and-admin.md`, Part 2, "Disabling a person" and "People, the install and monitoring", for the design this item delivers; `docs/plan/PLAN.md` for the intent; and `docs/plan/PARALLEL.md` for lanes and gates.

## Plan

Branch `core/p15-02-admin-people`, cut from `reboot`. Built on the owner's answers A1 and A2 and the recommended A5 (a few people), which `STATE.md` lists.

- **A person's numbers, one way** (decision record; changes how 0462 is held). `internal/adminview` may not reach `operations`, `usagereport`, `jobs` or `schedules`: each reaches a package that holds a person's words. A new leaf package, `internal/figures`, holds the numbers-only core that Operations and the admin both read: the report's settings and their bounds, the limits' keys, the measure of the cap, the memory reserve, the database, the files and the artifacts, the judge of a limit's state, the volume of a folder, the window of usage records and a model's health state. `operations` keeps its exported names and builds its report on it, so the person's page and the admin read the same function. What figures cannot read the same way without content (open tasks' budgets, failed and stuck tasks, the number of schedules) it counts from the same rows with narrow queries, and tests pin each count to Operations' own. It imports `tenant`, `tenantsettings`, `usage`, `models` and `settings`, and no package that holds content.
- **People.** `GET /api/v1/admin/people` gains, for each person: enabled (and since when), whether they have set a password, spend this month against the cap (spent, limit, warning level, state), the size of their database, files and artifacts, tasks failed in the health window and stuck, the number of schedules, model health as counts by state, and the keys of the limits whose watch level is crossed. Read on opening and on a refresh button, never on a timer (the recommended answer in `STATE.md`).
- **One person.** `GET /api/v1/admin/people/{id}/usage?from=&to=`: spend and calls by day and by model, failures counted by kind (model calls that failed or were refused, tasks that failed, schedule runs that failed; never their words), and storage over time from Operations' snapshots. The period defaults to this month and is held to `usage.report_max_days`.
- **The whole install.** `GET /api/v1/admin/install`: spend and calls for everyone this month, by model and by day, the sum of each person's figures; failures by kind; the disk (the volume of the data folder, with its watch level); the number of people, enabled and disabled; the server's version; the sampler's state (its interval and the newest snapshot across people). The install settings that were changed come with P15-03, which builds them.
- **Adding a person.** `POST /api/v1/admin/people` with a name makes the person (sealed, as `Install.Create` does) and returns a one-time setup code, good for `admin.setup_code_for` (24h, install). `POST /api/v1/admin/people/{id}/setup-code` gives a new one and ends any earlier one. Codes live in `data/admin/admin.db` (`setup_codes`, a new migration): only a hash, the person's id, the issuing account, when made, when it expires and when used. The door `POST /api/v1/setup` takes the code and a password: the code is used once, refused after it expires, refused for a disabled person; the password is set through `signin.SetPassword` and a session opens. The page `/setup` asks for both. Passkeys at setup wait for `signin.passkeys` (off as shipped): a person adds one from Settings afterwards. The admin never sees or sets a password. Each code made is in both logs.
- **Disabling and enabling.** `POST /api/v1/admin/people/{id}/disable` and `.../enable`. A disabled person is marked in their own database (`tenant_meta`, `disabled_at`), which every place that decides reads: sign-in refuses with 403 `disabled` ("ask the admin"), and a session cannot open while the mark is there (one statement); disabling ends every session in the same transaction; `unattended.Paused` reads as on, so schedules are held and background tasks, research and sub-agents pause through the switch that exists (decisions 0343, 0390), and the runner is woken at once (`jobs.Runner.PauseAll`); `share.Usable` answers revoked. Enabling clears the mark, moves every due time past now first (`schedules.Scheduler.Rearm`), so runs missed while disabled are not caught up, and wakes the runner. The person's own pause switch is left as it was. The admin view is handed these three hooks by `internal/app`, never the packages.
- **Both logs.** Every read and change of a person goes through `adminview`'s pair of entries in that person's log, with the account's name, as P15-01 built; a change records the old and the new value.
- **Operations splits** (decision record changing 0460). The disk leaves the person's Operations: their report keeps their own jobs, schedules, spend, storage and model health, and the volume is shown only in the admin account's Install. The sampler stops recording the disk in each person's database.
- **The registry.** The server's save of `keystone.json` first merges the tenant list from disk, so a person added from the command line while the server runs is kept (the recommended answer in `STATE.md`).
- **Settings** in `settings/core.json`: `admin.setup_code_for` (duration, 24h, install). The install disk's watch level reads `operations.watch_disk_percent` as the install has it.
- **Screens**, provisional on the drafts (`design/screens/Admin.html`, `Operations.html`): the admin page gains tabs People, A person and Install. People is the table of the draft with the new numbers, Add a person (which shows the code once), Disable and Enable, and Read again. A person is their numbers, usage by day and by model, failures by kind, storage over time, and a new setup code. Install is the totals, by model and by day, failures, the disk, the people and the sampler. `/setup` is the person's page for the code.
- **Proof.** Tests: the admin's numbers for each person equal `operations.Read` and `usagereport.Read` for that person, and the install's equal their sum, on two people with records, tasks, schedules and files; a disabled person cannot sign in, has no session, their schedule does not fire, their task does not run and their share link answers revoked, and enabling restores each; a setup code works once and not after it expires, nor for another person; marker words in a person's chats, titles and task errors appear in no admin reply; a person added from the command line survives the server's save. The `admin isolation` check gains `internal/figures` in the packages it holds, and its walk calls the new routes.
- **Left out.** Install settings and their changes (P15-03), views (P15-04), the marker-word drill over every route (P15-05), removing a person (the command line), passkeys at setup.

## Result

Built as planned, November 28, 2026; see `docs/architecture/people.md`, decisions 0700 to 0704 and the journal `docs/journal/2026-11-28-core-018.md`. The proof passes in tests: each person's numbers in the admin's list equal `operations.Read`, `operations.Watch` and `usagereport.Read` for that person (the database within the two log entries the admin's read itself writes), and the install's equal the sum of each person's; a disabled person cannot sign in, has no session, the scheduler holds their schedule, their switch reads paused and their share link answers revoked, and enabling restores each; a setup code works once, for its person, not after it expires or after a newer one, and never for a disabled person; no marker word of a person's reaches an admin reply. Changes from the plan: `GET /api/v1/admin/people/{id}` was added, for the person screen; the install disk's watch level is `operations.watch_disk_percent` as shipped until P15-03 makes install settings; the install settings that were changed are left to P15-03. Provisional on A5 (the recommended answer: a few people) and on a look in a browser: the screens type-check and build, and were not opened against a running server.
