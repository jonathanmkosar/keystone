## What was learned

- The name cannot be the mark. `tools/tenant`'s own comment gives `add "Test Person One"` as its example, and the isolation check makes a tenant with that name. A loader that trusted the name would put a published password on a tenant a person made. So the mark is a row only the loader writes, and a test proves a person with the same name is left alone.
- Writing the replies into the chat fixtures would have kept every reply twice: once in the chat and once in the recorded turn. Replaying is less to write and cannot drift. It also means `Read` can play every chat in memory, so a bad fixture is refused before any database is touched.
- Setting the password on every load would end the test tenant's sessions on every `rebuild`. The loader tries the fixture's password first and signs that one session out again. A test holds a session open across a second load.
- `rebuild` should not run the use cases against the data folder. The test tenant is there to be played with, and a chat the owner added to would turn `rebuild` red. `verify` runs them in a throwaway folder.
- The fake provider's step rule made a tool call in a fixture simple: the file gives the tool's result as the next message, and the request alone says the script is at step two.
- Loading stores no secret, so it never touches the operating system's key store and needs no `NewInstallKeeper`.
