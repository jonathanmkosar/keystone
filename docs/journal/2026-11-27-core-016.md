## What was done

- **`internal/adminaccount`**, new: `data/admin/admin.db` with migrations of its own (accounts, passwords, sessions, passkeys, prompts, and `admin_audit_log`, append-only by triggers as a person's is). Accounts have a 16-hex id and a name unique in any case; `AddAccount`, `RemoveAccount` (ends sessions at once, keeps log entries), `SetPassword` (ends sessions), `Find` by name or id. `SignIn` and `PasskeySignIn` open a session whose token is `ksa_` and 64 hex, kept as a hash; `Check` refuses a token of any other form before reading, and a session past `admin.session_for` or unused for `admin.idle_for`, and moves its last use. `Append` and `Log` keep the admin audit log in `audit.Entry`'s shape, scrubbed. Decisions 0650 and 0652.
- **`internal/signin/shared.go`**, new: the password rules, hash and constant-time comparison, and the passkey readers and signature check, exported without the database, so an admin signs in through a person's code under the `signin.` settings. The count of wrong tries is the same one statement, on the admin's own row.
- **The door**, in a new file `internal/api/admin.go`: the shell picks the token by its text (the admin cookie `keystone_admin`, path `/api/v1/admin/`, first on an admin path; the person's cookie first elsewhere). A `ksa_` token goes to the admin side, which checks the session, writes the admin log before and after (`admin:<account id>`), runs an admin route with `Call.Admin` and `Call.AdminSession` and no store, and refuses a person's route 403 `admin_account`. A person's side refuses every admin path 403 `not_admin`, in their own log. An admin route may be a door. Decision 0651.
- **`internal/adminapi`**, rewritten: the doors `POST /api/v1/admin/session` (name or id with a password, or a passkey) and `POST /api/v1/admin/session/passkey`; `GET` and `DELETE /api/v1/admin/session`; `GET /api/v1/admin/people`; the admin's own passkeys (`GET /api/v1/admin/passkeys`, `POST .../passkeys/prompt`, `POST .../passkeys`, `DELETE .../passkeys/{id}`). Every sign-in, good or refused, is in the admin log without the password.
- **`internal/adminview`**: asks that the admin account is in the admin database now, instead of the mark, and writes the account's name in each entry it leaves in a person's log (`{"by": ..., "read": [...]}`). `Person` has no `admin` field. Every person, the admin's own row gone, gets the two entries.
- **A person sees it**: `GET /api/v1/audit/admin` (`api.AdminEntriesRoute`, through `audit.ListByAdmin` in a new file) and Settings → Admin access, which folds each call's two entries into one row. Decision 0654.
- **`tools/admin`**, new: `add`, `password` (standard input), `list`, and `remove`, which refuses the last account without `--yes`.
- **Screens**: `/admin/sign-in` and `/admin` (`AdminApp.tsx`, drawn in place of the person's app for paths under `/admin`), and `AdminAccessSettings.tsx`. No mockup for either: provisional.
- **Removed** (decision 0653): `tenant.Tenant.Admin`, `SetAdmin`, `IsAdmin`, `Marks`, the save that merged marks and the backup's two lines (`internal/tenant` is back to its state before the first pass, plus `dir.go`); `tools/tenant admin` and its `ADMIN` column; `signin.StepUp`, `BeginPasskeyStepUp`, `PasskeyStepUp`, `EndStepUp`, `Session.AdminUntil` and the `checkPassword`/`checkAssertion` split (`signin.go` and `passkey.go` are back to their state before the first pass, plus the `last_sign_in` write; `LastSignIn` moved to `lastsignin.go`); the step-up routes, `api.Route.StepUp`, `api.ActorAdmin`, 401 `step_up`, and `admin` and `session.admin_until` in a person's session answer (`shell.go` back to before the first pass); `admin.step_up_for`. A forward migration, `20261127T170000_admin_step_up_removed.sql`, drops `admin_until` and the `step-up` prompt purpose; the two step-up migrations stay as they ran.

## Questions, each with a recommended answer

1. **Should the admin database be encrypted at rest with P15-06?** It holds account names, password hashes, passkeys' public keys and the admin audit log, no person's data. Recommended: not now; add it to P15-06's list if the owner wants a copied data folder to show nothing of the admin either. Built: plain.
2. **Should removing the last admin account need more than `--yes`?** Recommended: no, as for the first pass; whoever runs the command line owns the data folder and can add another. Built: `--yes`.
3. **Admin sign-in by name or id.** A person signs in by picking their name from the list; the admin's door lists nothing (a list would tell anyone the admin's name) and takes the name typed, or the id. Recommended: as built.
