# Core 010, 2026-11-25

Item done: P13-04, backup and restore. Built in its own worktree, on the branch `core/p13-04-backup-restore`, cut from `reboot` at 81ae80b.

The owner uses Keystone daily with real chats and real provider keys, and until now a copy of his data folder could not carry those keys to another machine. This pass made one tenant into one sealed file, and a restore that brings it back anywhere with its keys working.

## What was done

- A new package, `internal/backup`: the file. A header (magic `KSB1`, the key derivation, its rounds, a salt, a passphrase check), then the contents in 64 KiB chunks sealed with AES-256-GCM, each nonce a counter with a last-chunk flag and each chunk bound to the header. The key is PBKDF2-SHA-256 from the standard library, split three ways by HKDF. Inside: a gzip-compressed tar, with every name checked on the way in and on the way out. Plain functions and two small types, `Writer` and `Reader`.
- In `internal/secrets`, a new file `rewrap.go`: `Rewrap`, `Vault.Rewrapped` and `KeyKeeper`. A secrets file's data key is unwrapped by one keeper and wrapped by another; the secrets are opened only to check them. `secrets.go` had `read` and `write` split so a file's bytes can be parsed and encoded without a path.
- In `internal/tenant`, a new file `backup.go`: `Install.Backup`, `CheckBackup` and `Install.Restore`, with `BackupOptions`, `BackupInfo`, `RestoreOptions`, `Restored` and `ErrTenantExists`. `tenant.go` had `open` split so `openStore` can open a restored folder before it is in the registry.
- In `tools/tenant`, `backup <tenant-id> <file>` and `restore [--replace] [--check] <file>`, in a new file `backup.go`. The passphrase comes from standard input only.
- Two settings in `settings/core.json`: `backup.passphrase_rounds` (2000000) and `backup.passphrase_min_length` (12).
- A new surface in `verify`'s `no keys in output`, `backup and restore`, in `tools/verify/backup.go`.
- Docs: `docs/architecture/backup.md`, the runbook `docs/runbooks/backup-and-restore.md`, the "After a restore" section of `docs/runbooks/secrets.md` rewritten, sections in `secrets.md` and `tenants.md`, rows in the overview and `internal/README.md`, paragraphs in `tools.md`, decisions 0260 to 0263, and the line on backups in `PLAN.md`.

## What was learned

- The plan's "a backup of one tenant is its folder" could not hold. The folder's chats are in the clear and its keys open only on the machine that wrote them. Decision 0260 changes the plan's line.
- The keys could travel without any package but `internal/secrets` seeing one. Wrapping the data key again, from the install's keeper to a keeper made from the passphrase and from that to the new install's, is one function, and a backup file is just another keeper.
- A file cut exactly at a chunk's edge is the case a simple chunked format misses. Marking the last chunk in its nonce, and reading one byte past each full chunk to learn whether it is the last, closes it. gzip reads through a buffer of its own unless its reader can give one byte at a time, which would have hidden bytes after the end; the chunk reader gives bytes one at a time for that reason.
- "Check before writing anything" needs two readings of the file. Keeping the key made from the passphrase between them means the rounds are paid once, and a SHA-256 of each reading proves it was the same file both times.
- `internal/tenant` cannot import `internal/signin`, which imports it, yet a restored tenant should start signed out. `RestoreOptions.Ready` runs on the restored store before it is put in place, and the command passes `signin.SignOutAll`. A failing step there still leaves nothing.
- `VACUUM INTO` makes a consistent copy of a database another connection is writing, so a backup runs beside the server. A test holds a write open during a backup and finds only what was committed.
- A restore changes `keystone.json`, which the server holds in memory and writes back whole, so the server must be stopped for a restore. The same is true of `tenant add` today; the runbook says it for restores.
- An empty tenant's database is 344 KB and its backup 10 KB: the schema and its full-text tables compress well.
- A flip in the high byte of the rounds names sixteen million rounds, which takes two seconds to refuse. The test leaves those bytes alone and checks a count out of bounds instead.

## What was verified

On Windows 11 with Go 1.26.0, in the item's worktree:

- `gofmt -l .` prints nothing and `go vet ./...` is clean.
- `go run ./tools/verify`: 19 of 19, before each commit, with the new surface inside `no keys in output`.
- `go test ./internal/backup ./internal/secrets ./internal/tenant ./tools/tenant`, as listed under "Checked by" in `backup.md`. The item's proof is `TestABackupRestoredOnAnotherMachine` in `tools/tenant`: a tenant with a password, an open session, two chats, a file and a stored secret is backed up through the command, restored into a fresh data folder under another memory keeper, signs in, its old session is refused, its chats list, read, search and hold their file, and its secret comes back.
- That no restore writes before its check: for a wrong passphrase, a changed byte and a cut file, the new install's keeper is never asked to wrap, and the data folder is byte for byte as it was.
- The new `verify` surface was run on its own first, through a throwaway test since removed: 33 outputs, none holding the value, and every refusal printed as expected.
- By hand, with the real keeper (DPAPI) in throwaway folders inside the worktree, since removed: `tenant add`, `secret set` and `password` with invented values; `backup` took 0.6 seconds with the shipped rounds and wrote 10 KB; `restore` into a second data folder listed the secret; a second `restore` was refused with the hint; `restore --replace` replaced the tenant in the first folder; `keystone serve` on port 7917 over the restored folder, then `keystone signin` as the restored tenant and `GET /api/v1/secrets` listed `provider.test`. The server was stopped.

Not run:

- A restore on a second physical machine, or under another Windows account. The keepers used were two memory keepers, two key files in `verify`, and DPAPI on one account.
- macOS and Linux. The test of a link in a tenant's folder skips on Windows without the right to make links.
- A tenant with real uploads or artifacts: no item writes them yet, so the tests write files into both folders by hand.
- `rebuild`.

## Provisional

The item is done: its proof passes, and it has no owner gate. Two things are short of what a person might expect.

- **No schedule** (decision 0263). A backup is made only when the command is run. A schedule needs a key no one has to type, which means a public-key format, and a job on the background jobs P8-01 is building.
- **Restore on another machine is proven with stand-in keepers.** The code path is the same for DPAPI, which was run by hand on one account.
