## What was done

- **A package of its own.** `internal/project` is the scripts' helper package, so Keystone's projects are `internal/projects`. It reads no setting and does not import the chat record (which does), so it is a guard of fixed rules 1 and 3 in `fixed rules`, as `internal/attach` is.
- **The record** (migration `20261125T214700_projects.sql`): `projects` (name, instructions, memory space, archived), `project_files` (each file by its SHA-256, with its name, media type, size, the text read once, and a sensitive mark) and `project_chats` (a chat in one project or none; both columns refer to the tenant's own rows with `ON DELETE CASCADE`). Create, rename, change the instructions, archive and bring back, delete (the chats are kept, decision 0402); add, mark and take off files; start a chat in a project, move one in, between and out.
- **Files behind two seams** (decision 0401): the bytes in `files/` under their SHA-256, written whole through the store's `os.Root`, as the uploads lane (P9-02) names its own; the text from text formats only, by ending, UTF-8 with no zero bytes. `Blobs` and `TextReader` are interfaces with one implementation each, so the integrator can make the two stores one. A file goes only when no project file and no chat (`chat_files`) names it, and `chat.Delete` gained one condition so it keeps a file a project holds.
- **Into each call** (`internal/turn/projects.go`, four added lines in `context.go`): the instructions, under a heading, in the context builder's `project` part, which was waiting for this item in the standing start, so the first cache point covers them; the files in the `attached` part after the attached chats, each cut to `projects.file_context_max_chars`, within `chats.context_attached_percent`. A chat in no project carries neither.
- **Fixed rule 3** (decision 0403): a file marked sensitive reaches a call only when every model of its route may read it, after `recall.Hold`; otherwise a pinned line counts what was left out. A project with a sensitive file holds a chat's route when the chat's own model may read it (one added line in `Runner.sensitive`).
- **Project memory** (decision 0400): the store interface has spaces and no tags, so a project's memory is a space, named when the project is made (`project-{slug}`) and kept when it is renamed. The memory pass writes a project chat's facts there (one added line in `memoryPass`); a held chat's facts still go to the sensitive space or nowhere. Recall searches through `projects.Prefer`, which asks the project's space first and passes every label through (one added line in `searchKnowledge`).
- **Thirteen routes**, listed in `internal/app`: `/projects`, `/projects/{id}`, its files (the raw body with `?name=`, as uploads do), its chats, and `GET /chats/{id}/project`. `docs/api/openapi.json` regenerated.
- **The screens**, provisional: projects in the sidebar, `/projects` with its cards and form, `/projects/<id>` with the name's menu, a composer that starts a chat in the project, its chats, and the instructions, files and memory panels, and a chip after a chat's title that moves it in, between and out. New files `Projects.tsx`, `projectStore.ts`, `projects.css`; added lines in `Shell.tsx`, `api.ts` and `Icon.tsx`, and one changed line in `App.tsx`. `web/dist/` was built to look at it and not committed.

## What was learned

- The item was mostly joining what was there, again: the `project` part and the attachments' share were in the builder, and attached chats had already settled how a sensitive item is left out or holds the route. The new code is the record, the files, the routes and the screens.
- Two lanes writing to one `files/` folder must each know the other's holders before removing a file. The chat record already counted only chats; a project file of the same bytes as an upload would have been removed with the chat. Counting both ways on this branch closes it here; the uploads branch needs the same one condition at the merge.
- Decoding JSON into a reused struct keeps a pointer field an omitted key does not mention: the first version of the proof read "the chat outside is in the project" because `where` still held the last answer. Each read now starts from a zero value.
- Embedding a struct whose JSON has `added` (a time) and adding `Added bool` beside it hides the time silently. The flag is `new`.
- Two stylesheets in the bundle define `.button-danger`, and the later one (`scheduled.css`) sets only the text to the error colour, so the button's text is the colour of its ground. It shows in the chat's own Delete confirmation too. The project's confirmation sets its colours itself; the shared rule is the interface lane's to settle.
- On a phone, a chip with the project's name crowded the header into the Hand off button; it is its icon alone there, with the name in its label.

| Question | Recommended, and built | Holds up |
| --- | --- | --- |
| When a project is deleted, are its chats deleted too, or kept as ordinary chats? | Kept: a chat is a record of what was said, and a person can delete chats themselves (decision 0402) | Nothing |
