## What was learned

- **The server already remembers a chat's model.** A turn that names a model and opens it writes the name on its row, and the next turn and the model route take the model of the chat's newest turn that has one. So the page sends a pick once and keeps nothing (decision 0240). If the model does not open, or the turn is refused as `sensitive`, nothing is written and the chat stays where it was. In a held chat a hosted pick with a local fallback behind it is left out of the route, and the turn records the fallback.
- **The model route does not say a chat is held.** `reason` is set only when there is no model at all, and `source` says where the model came from. The only signal is the turn the server refuses with the code `sensitive`. The picker reads that turn and keeps a mark in local storage (decision 0241).
- **The model route lists models whose key is missing**, because the registry's usable list checks the entry and not the vault. The server's own choice can be such a model, and the turn then fails as `model_unavailable`. The picker reads `key_present` from `GET /api/v1/models` and says so on the button.
- **A new chat has no model route.** The page works the choice out from the registry and `chats.default_model`, in the server's order. The test tenant's model is in no registry, so it has no picker on the new chat screen.
- A menu that hangs from the picker runs off the left of a phone's screen: the picker sits right of centre and the menu is wider than the room beside it. On a phone the menu now hangs from the whole composer.
- The browser pane can hold tabs the person opened. Two read-only calls of a check script went to another open tab, another Keystone, because the active tab had changed under it; both were refused with 404. Every call after that named its tab.
