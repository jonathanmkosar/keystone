## What was done

- `internal/knowledge/memory`, a new package and a guard of fixed rule 3. It imports the knowledge interface, the seam, routing's kind names, usage and the tenant handle, and reads no setting; it does not import the chat record, which does.
  - `Request` asks for the facts of one exchange: the prompt as the system text and one message with the chat's title, the day, the person's message and the reply, each cut at a word's end. `Facts` reads the answer as one JSON object, `{"facts": [...]}`, from the first `{` to the last `}`, and leaves out blank, long, repeated and extra facts.
  - `Target` says where the facts may land before any model reads: the memory space, or for a chat that was sent sensitive content only a sensitive space the store's catalog confirms, and otherwise nowhere. `Add` adds them as one source whose origin is `keystone://chats/<chat>/turns/<turn>`, refuses sensitive facts from a model that may not read them, and reads the label they landed with.
  - `Queue`, `Claim`, `Interrupt`, `Finish`, `Get`, `Passes` and `Waiting` over `memory_passes`; `Incognito` and `SetIncognito` over `memory_chats`; both from the migration `20261125T140000_memory_pass.sql`.
  - `NewReserve` and `Allow`: the memory pass's monthly reserve, against `usage.SpentOn`, new in `internal/usage/kind.go`.
- `internal/turn/memory.go`, a new file: `memoryLater` queues a done turn's pass and starts the chat's worker beside the turn, one worker per chat, which marks passes a stop left running as interrupted and works the queue oldest first. Each pass reads the settings, opens the store, asks `Target`, reads the exchange from the chat record, routes the `memory` task (the test tenant gets its recorded turns), calls through `Runner.call` with `stepMemory`, reads the facts, asks again whether the chat was held, and adds the source. The memory route's gate is the reserve and then the cap. Three routes: `GET /chats/{id}/memory`, `PUT` and `DELETE /chats/{id}/incognito`.
- Eleven settings in `settings/knowledge.json`: `knowledge.memory`, `knowledge.memory_space`, `knowledge.memory_sensitive_space`, `knowledge.memory_reserve_usd`, `knowledge.memory_prompt`, `knowledge.memory_source_name`, `knowledge.memory_max_facts`, `knowledge.memory_fact_max_chars`, `knowledge.memory_message_max_chars`, `knowledge.memory_max_output_tokens` and `knowledge.memory_timeout`.
- Fixtures: `fixtures/test-tenant/turns/memory.json`, the replies to two messages with durable facts in them and the extraction of each, the extraction of the held question, and an empty list for any other exchange; `fixtures/test-tenant/knowledge/memory.json`, the messages, the facts each must give, a message with nothing durable, and the held chat's question, space and facts.
- `tools/verify/memory.go`: the check `memory pass`, which makes 20, and the package's line in `fixedRuleGuards`.
- Docs: `docs/architecture/memory-pass.md`, decisions 0280 to 0284, rows in the overview and in `internal/README.md`, lines in `tools.md`, `turns.md`, `routing.md`, `usage.md`, `knowledge.md`, `test-tenant.md` and the fixtures' README, and `docs/api/openapi.json` regenerated for the three routes.

## What was learned

- The test tenant's own knowledge decides which chats are held. The first fixture asked "Can you suggest a supper", and the built-in store stems "suggest" to match "The clinic suggested no screens after nine" on the sensitive page: recall kept it for the local model, the chat was held, and the memory pass, rightly, kept its facts nowhere. The check failed on it, and the fixture's messages were changed to ones that recall nothing sensitive. The bakery question has the same word, so the check's message with nothing durable is the sea poem, which the recall check already proves recalls nothing.
- The memory pass talks to the hosted model of the `sensitive content` check's invented tenant after every ordinary turn, in the background, so a memory call from one step can land between that check's counts in the next. The check now switches the pass off for that tenant; the memory pass check proves rule 3 for itself, with a hosted model the memory rule names.
- A store makes a space it does not hold as a normal one. So naming a sensitive space is not enough to send sensitive facts to it; the store must say, in its catalog, that the space is sensitive. That rules out a fresh space holding only sources, which is a cost written in decision 0281.
- The check after the call earns its place. With the hold ignored before the call, by hand, the facts still went to the sensitive space, because the second question caught the chat being held; only the step that expects no model to read a held chat with no sensitive space caught the fault.
- Compaction skips a chat whose job is running; the memory pass cannot, or a person who writes quickly to a slow local model loses facts. A queue in the database was the smallest thing that keeps every turn's pass and also records what became of it.
- Every test passed on its first run, which proves nothing about the tests. Faults were put in by hand: no reserve on the memory route, an incognito turn queued, and the hold ignored. Each was caught by `go test ./internal/turn`, and the first and last by the `memory pass` check run on its own. They were taken out again before the commit.

## Questions for the owner

1. Is the memory pass's reserve a part of the monthly cap, or a part set aside from it?

   Recommended: a part of the cap, as built. What the memory pass spends counts against both; chats are not limited by it; at the cap the memory pass stops with the chat, unless a local model is in its route. Setting it aside would lower every chat's cap by the reserve, unasked, and the owner's memory pass on his local model costs nothing.

   Assumed meanwhile: a part of the cap, $2 a month (decision 0280).

   Provisional because of it: nothing.

2. Facts from a chat that was sent sensitive content are kept nowhere until a sensitive space is named. Should the owner name his?

   Recommended: yes, the sensitive space in his Waymarks that holds pages, with `knowledge.memory_sensitive_space`. Keystone confirms it from the catalog before it sends anything there.

   Assumed meanwhile: empty, so such facts are kept nowhere and no model reads those exchanges.

   Provisional because of it: nothing.

3. Should incognito keep a chat out of recall too, and keep no record, now?

   Recommended: no, not in this item. The flag stops the memory pass, which is what P6-06 asks; keeping no record touches the chat record, recall and the screens, and belongs with the memory screens (P6-07).

   Assumed meanwhile: the flag stops the memory pass and nothing else.

   Provisional because of it: nothing.
