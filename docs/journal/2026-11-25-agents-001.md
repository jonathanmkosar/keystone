Item provisional: P7-01, the tool loop. It waits on the owner's approval of the agent mockups (P1-05), for how the steps look. Everything else in the scope is built.

The item was started by one session, which wrote the plan and most of the server side and stopped when its usage ran out with the work uncommitted. A second session read that work, kept its design, finished the server side, and built the checks, the screen and the docs.

## What was done

- A new package, `internal/tools`: the registry. A tool is a struct (a name, a description, a JSON schema, `ReadOnly`, and one function), a registry is made with `tools.New()` and filled with `Add`, and `Registry.Run` is the only way a tool runs. It records the call in the audit log before and after, asks the approval rule, runs the tool in a goroutine of its own under the turn's context and a timeout, and turns a failure, a panic, a timeout, bad input or an unknown name into an error result. `Decline` answers a call without running anything and records it the same way. The package reads no setting.
- `internal/tools/approval`: fixed rule 2's test, `Check(readOnly, approval)`. An `Approval` can be made only inside the package, and nothing makes one yet, so every tool that changes something is refused with a result the model reads.
- `internal/tools/builtin`: three tools that only read, `current_time`, `search_chats` and `read_chat`. Each reaches the person's chats through the store it is given and nothing else.
- `internal/app/tools.go`: `app.Tools(c)` makes the server's registry and adds the built-in tools by one plain call. `app.Config.Tools` lets a caller give its own.
- In `internal/turn`, a new file, `tools.go`: which tools a call offers (into the context builder's `Tools` slot), what happens to a model's calls, and the step limit. At `chats.turn_max_steps` the last calls are declined, a note is written as the turn's last message with the stop reason `step_limit`, and the turn ends as `done`. Stop cancels a running tool, and every call is still answered and stored.
- Five settings in a new `settings/agents.json`: whether tools are offered (tenant scope), the tool timeout, the most characters of a result, the note at the step limit, and how many messages `read_chat` returns.
- The test tenant's recorded turns gained `turns/tool-steps.json`: a task of several steps (search the chats, read the time, answer) and a call to `send_postcard`, a tool that would change something.
- In `verify`: a new standing check, `approval`, and the tool calls' part of `calls recorded`, both in a new file, `tools/verify/toolloop.go`. `internal/tools/approval` and `internal/tools` are the guards of the approval rule in `fixedRuleGuards`.
- The screen: each tool step is a readable line, written by a new file, `web/app/src/steps.ts`, from the tool's name, input and result; running, then answered, with a few words on the right; collapsed until opened; and the step limit's note in a box of its own. `web/dist/` is rebuilt.
- The doc `docs/architecture/tool-loop.md`, a row in the overview, three lines in `componentDocs`, a row in `internal/README.md`, a section in `web.md`, lines in `turns.md`, `context.md`, `tools.md` and `test-tenant.md`, and decisions 0200 to 0204. Decision 0143 has a line saying what replaced it.

## What was learned

- The contract held. `tool_call` and `tool_result` already had every field the loop needs, and the screen already drew a step from them. The one addition is a value of `stop_reason`, so `docs/api/openapi.json` came out the same file when it was regenerated: it lists `stop_reason` as a string.
- The step limit was the one place the old behaviour had to go. Failing the turn put a red error and a retry on the screen for a limit the install set on purpose, and left the last calls with no result. Declining them and writing a note keeps the record one a provider takes, and the note is still there after a reload (decision 0202).
- A tool that ignores its context would hold a stopped turn open if the turn waited for it. Running it in a goroutine of its own and returning on the context makes stop and the timeout real for any tool (decision 0203).
- The record keeps a tool result's words and no status. So the screen tells "not run" from "failed" by the server's own sentences, which is cheap now and fragile if they change (decision 0204). The first look at a step limit in the browser said "Checked the date and time" over a call that never ran. A row with no result now says what the model asked for: "Check the date and time", with "not run".
- `search_chats` counts matching messages, not chats, so the test tenant's one lighthouse chat comes back as "3 matches". That is what the result says, and it is what the row says.
- `app.turnOptions` could not be given the registry by changing its one line, because `internal/app/app.go` takes added lines only. The added lines call it again with a mark set and add the registry to what it returns. An integrator may fold the two into one literal.

## What was verified

On Windows 11 with Go 1.26, in the worktree for this item:

- `gofmt -l` prints nothing for `internal`, `tools` and `cmd`.
- `go test ./internal/tools/...` and `go test ./internal/turn` pass.
- `go run ./tools/verify` is 17 of 17, before each of the three commits.
- The `approval` check was seen to fail, with four problems, when `approval.Check` was changed to let everything run, and to pass again when it was put back.

The item's proof:

- The scripted task of several steps completes, in `go test ./internal/turn` and in `verify`'s `calls recorded` on the real server: the fake model calls `search_chats`, reads the result, calls `current_time`, reads that, and answers. Both steps are in the stream, the chat record, the context record and the audit log under the turn's request id.
- The step limit ends a turn as done with its note, and the chat goes on. A tool that changes something never runs. A tool that fails, panics, runs too long or does not exist gives an error result and the turn goes on. Stop cancels a running tool, and the call after it never runs. A tool given another tenant's chat id reads nothing.
- In a browser, against `bin/keystone` built from this branch on port 7921 with a data folder inside the worktree, signed in as the test tenant: the task of several steps rendered as two step rows between the model's words ("Searched your chats for “lighthouse”" with "3 matches", then "Checked the date and time"), each opened to show the tool, what was sent and what came back, and the same after a reload. The postcard turn showed "Used send_postcard: …" with "no such tool", because the shipped server has no such tool.
- With a stand-in server built for the look only, from the same code with a slow `search_chats`, a step limit of two and a `send_postcard` that changes something (not committed): the running row ("Searching your chats for “lighthouse”", pulsing, "running"), the step limit's note, "Check the date and time" with "not run", and the postcard refused by the approval rule with "not run" and the reason in its open body. In dark and light, and at phone width. Both servers were stopped.

Not run: `go run ./tools/rebuild`, any system but Windows, any real model, and the race detector.
