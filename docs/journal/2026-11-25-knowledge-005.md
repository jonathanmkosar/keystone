## What was learned

- Recall and routing each need the other's answer. Recall gives less to a model that may not read sensitive content; routing keeps such a model out of a call that holds some. The way through is order: search once, with no model in mind, and keep everything a model of either kind could be given; then route; then build.
- A route is one provider, and it sends the same request to whichever model answers. The turn built each call for the first model of the route. That was already a leak, waiting for the first sensitive content to arrive: the whole person map, built for a local model, would have gone on to a hosted fallback. The `sensitive content` check found it at once when the build was made the old way on purpose. Building for the least of the route closes it for the map, for recall and for the lookups together (decision 0210).
- A reply that repeats sensitive content is sensitive content, and it is in the chat's history. So the mark belongs on the chat, and it is never taken back (decision 0211).
- Both stores match on any one word, so a whole message as a query finds nearly every page. Leaving out the words that say nothing of a message is enough for the fixtures, and the list is a setting.
- The first version of the checks passed on the first run, which proves nothing about the checks. Three faults were put in by hand and each was caught: routing never told "sensitive", a call built for the first model of its route, and recall giving nothing. The faults were taken out again before the commit.
- The Waymarks adapter's tests have a full fake, but in a test file no other package can import. The checks have a small one of their own that answers the five read calls recall uses.
- The person map waits for the Waymarks adapter's own timeout, not recall's. A turn against a Waymarks that never answers is held for the adapter's five seconds by the map, while recall gives up at its own. The test of recall's timeout calls the search directly for that reason.

## Questions for the owner

1. Should the person map alone hold a chat to local and trusted models, as recalled content does?

   Recommended: no. The map is kept out of every call that may reach a hosted model, because each call is built for the least of its route. Holding the chat as well would close hosted models to every chat a person with a sensitive space has on a local model. What it leaves open: a reply on a local model that repeats a title from the map can reach a hosted model later in the same chat, if the person moves it there.

   Assumed meanwhile: the map does not hold a chat (decision 0211).

   Provisional because of it: nothing built. Holding on the map too is a few lines in `internal/turn`.

2. A chat that was sent sensitive content stays held for good: a new chat is the only way back to a hosted model. Is that right, or should the person be able to release a chat, with a warning?

   Recommended: held for good. Releasing it would send the history, which may repeat the content, to a model rule 3 says may not have it.

   Assumed meanwhile: held for good.

   Provisional because of it: nothing.

3. Is what the knowledge store holds "outside content" for the approval rule (P7-02)? A source can be an imported document or the facts from an email, written by someone else.

   Recommended: a source is outside content, and a page is not. A turn that recalled a source, or read one with a lookup, then has every side-effect tool ask. Pages are written by the person and by Keystone's own upkeep jobs from sources, which is a second question for P8-06.

   Assumed meanwhile: nothing; there is no approval policy yet. Each recalled item and lookup result says whether it is a page or a source, so P7-02 can tell.

   Provisional because of it: nothing built here.
