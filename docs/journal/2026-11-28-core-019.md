## What was done

- **The install's values in `keystone.json`** (decision 0710): two objects, `settings` for install settings and `person_defaults` for the default each person's own setting starts from, kept by `internal/tenant/installvalues.go`, read from disk at each read, and written with every field and key it does not know. `data.dir` is refused; `server.address` is read from the file when `--address` is not given.
- **One overlay on the registry** (decision 0711): `settings.UseInstalled`, `Registry()` giving each install value as its `Default`, `settings.Shipped` and `settings.DefaultFor`. `tenantsettings` falls back to `DefaultFor`, so every setting read through it, the turn's and the router's included, follows a change at once, and a person with no value of their own follows the install's default (decision 0712).
- **`internal/installsettings`**: `Load` at start (from `keystone serve`, before any setting is read), `List`, `Get`, `Check`, `Set` and `Clear`.
- **The registry's `restart` field** (decision 0713), on install settings only, marked on the 172 the server reads once at start; a change to one is kept and waits for the next start. A test in `internal/app` holds the marks for everything `app.ReadConfig` reads.
- **Four admin routes** (`internal/adminapi/settings.go`, through `internal/adminview/settings.go`): `GET` and `PUT /api/v1/admin/people/{id}/settings` for a person's `tenant-admin` settings, and `GET` and `PUT /api/v1/admin/install/settings` for the install's values and person defaults. Each change is in both logs with its old and new value; a refused change touches nothing of the person's; an install change is in the admin log alone (decision 0714).
- **Screens** (decision 0715), provisional on the mockups: `/admin/settings` (the whole install, and each person's starting defaults), `/admin/people`, and `/admin/people/{id}/settings`, drawn from the registry by scope, so the router's policy (P14-05) appears with no change here.
- The OpenAPI document regenerated.

## What was learned

- The turn runner and the router read a person's settings through `tenantsettings.Get` with a registry kept for the server's life; making `tenantsettings` fall back to `DefaultFor` was enough for every one of those to follow an install change, with no change in the chats or models lanes.
- What the server copies once at start is mostly `app.ReadConfig`, so the restart marks could be found by running it with a recording `get`, and the same trick is the test.
- `Set-Content -Encoding utf8` in Windows PowerShell 5.1 writes a byte-order mark; the item file was mended at once.
- With seven lanes running verify on one machine, the load test missed a timing figure under load: `TestTheSmallLoadStaysInsideItsBudgets` (a reply for one person, 1.31 s over 1 s) on the plan's first run, and `TestTheFastPathLeavesWhatARealTurnLeaves` (a turn that did not end as done) on the build's first. Each passed alone and on the next full run; nothing in the load test or its settings was changed.
- The worktree has no `node_modules`, and installing packages was not done. The web code was type-checked with the main checkout's TypeScript and type packages, read only, through a throwaway `tsconfig.json` outside the repo; `web/dist` was not rebuilt.

## Provisional, and why

- **The person defaults** (the owner gate): built as the default anyone who has not chosen follows (decision 0712).
- **The screens**, on the mockups: the Admin draft has a Settings tab and no drawing of it.

## Questions, each with a recommended answer

1. **Does a person default reach people who have not chosen, or only people added after it?** Recommended: everyone who has not chosen, as built (decision 0712); a person's own choice always stays theirs. The other way is a copy written at `Install.Create`.
2. **Should the admin also set install-wide defaults for `tenant-admin` settings**, such as one router ladder or one monthly cap for everyone, with each person's own setting on top? Recommended: not now; with a few people, setting each person is enough. Built: not offered (the install route refuses a `tenant-admin` key).
3. **Should the admin see how many people follow a default?** Recommended: not now; a count per setting would say it without showing anyone's value.
