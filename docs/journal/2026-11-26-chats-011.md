## What was done

- **What New Keystone keeps, read from its source.** It has no chats: a workspace is one continuing conversation, a row in `jobs` for each turn and at most two rows in `messages`. Its `events` say what happened in a turn in safe short words, never a tool's input or result. Routines are prompts on a cadence, in America/Chicago. Its artifacts are built apps whose files are on disk. Nothing is marked sensitive.
- **The record** (`internal/imported`, migration `20261126T022700_imports.sql`): `imports` (runs), `import_sources` (every source id brought, kept for good), `imported_chats` (the mark a chat wears) and `imported_messages` (the model named for a reply).
- **A chat written with its own times** (`internal/chat/imported.go`): `chat.Import` writes a whole chat and its search rows in one transaction and runs the caller's function inside it, so a chat and the record of where it came from are written together.
- **The importer** (`internal/importer`): `OpenSource` (read-only and immutable, after refusing a file with a log beside it, a damaged file and a file that is not New Keystone's), `Copy` (`VACUUM INTO`, for a database in use), `Read`, `MakePlan` (pure: the dry run and the import see the same plan), `Check`, `Run` and the report.
  - A routine's run and a build are each a chat of their own. The rest is cut into chats wherever more than `chats.import_chat_gap` (1h) passed; a title is the first words of the first message (decision 0510).
  - Messages are plain text with their original times and roles. A reply's web sources are a list at its end; a text attachment is a second block. The model New Keystone named is kept with the reply and given by the API.
  - Events are counted by kind in the chat's note, not recorded as steps (decision 0511). An imported chat has no turns (decision 0512).
  - Each active or paused routine with a cadence Keystone has becomes a paused schedule through `schedules.Scheduler.Create`; a person with no time zone gets New Keystone's (decision 0516). The morning brief is known by its id.
  - Notebook entries, drafts, decisions, proposals and built apps are counted and left (decision 0514).
  - No imported chat is held by default; `chats.import_hold` holds the chats New Keystone read the wiki in, or all, in the chat's own transaction (decision 0513).
  - A run has a started and an end entry in the audit log, calls no model, and prints no word of the source (decision 0515).
- **The command**: `tools/tenant import [--check] [--workspace <name>] <tenant-id> <copy>` and `tools/tenant import-copy <workspace.sqlite> <new file>`.
- **The mark**: `imported` on `Chat` from `GET /chats`, `GET /chats/{id}` and `PATCH /chats/{id}`; an "imported" mark on the chat's row and a line at the top of the chat (`Imported.tsx`). `docs/api/openapi.json` regenerated.

## What was learned

- The hard part was not reading New Keystone's tables but deciding what a chat is, since it has none. A gap in time is the only mark of a sitting the database holds, and New Keystone sent each call only the last few messages, so a sitting is also what its replies could see.
- A New Keystone job looks like a Keystone turn, and writing each as a row in `turns` would have shown the model with no added line. It would also have filled Operations' list of recent turns with a hundred that never ran here, since that list is in the order rows were written. Imported chats have messages and no turns, as the test tenant's loaded chats do.
- Holding a chat needs a turn: `turn_recall` hangs on `turns`. So a held imported chat has one turn that calls no model, written by the importer in SQL in the chat's transaction, because `recall.Hold` on a store with one connection cannot run inside another transaction.
- New Keystone's "artifacts" and Keystone's share a name and nothing else: a manifest of a built app against a document with versions.
- A database in write-ahead mode cannot be opened read-only on Windows without SQLite making files beside it, unless it is opened as immutable. So the import reads an immutable copy, and `import-copy` reads a database at rest as immutable too; only a database some program already has open is read through its shared-memory file. The first hand run showed the files; a test now counts the folder.
- The scratchpad folder is shared by every session on this build. Staging files there under a plain name (`stage/`) picked up another session's files from a day earlier and copied them over two files of `internal/operations` in this worktree. It was seen in `git status` at once and undone with `git checkout`; nothing of it was committed. New files are now written in the worktree, and anything in the scratchpad carries the item's id in its name.
- The harness refuses a shell command it cannot prove stays in the worktree, including one whose path holds the word "source". Shared docs were edited one line at a time with the editor.
- A proof that decodes several replies into one variable keeps the fields the newer reply lacks: an imported chat's mark stayed on the next chat read. Each reply now has a fresh value.
