## What was learned

- The contract arrived about half way through. The parts that did not need it were built first: the Markdown reader, the event reader, the conversation, the composer and the styles. Only `api.ts`, the store of arriving replies and the step from messages to items waited, and they took the contract's shapes as they are.
- The page stops reading a turn's stream at `end` and does not wait for the server to close it. In the browser's network log a stream ended that way is marked as aborted. That is the page's doing and not a fault.
- The stream's first request is a `POST`, so `EventSource` was never a choice. `fetch` with a hand-written reader is about sixty lines, and it lets the page see a refused stream and decide when to come back (decision 0151).
- The content security policy refuses a `style` attribute in markup and allows a style set on an element from script. So the composer can grow with its text, and nothing else on the screen sets a style.
- The person's bubble in the mockups is not a token, but it is exactly halfway between the raised ground and the line in both themes. `color-mix` gives it from the two tokens.
- The record keeps tool results in a message with the role `user`. Drawn as it is stored, a reply that used a tool would be cut in two by an empty bubble. The screen folds a run of assistant messages and tool results into one reply.
- A model's Markdown, read again from the top on every redraw, is fast enough for a reply. Redraws are held to one every 24 milliseconds.
- `GET /api/v1/chats` on a server with no chat routes answers 404 with the code `no_route`. The app used to read every 404 as "the server is not ready". It now reads the code, so a chat that is not there is told apart from a route that is not there.

## For the integrator

1. **Merge order.** This branch touches only `web/` and docs. It does not need P4-03 to build or to pass `verify`. It needs P4-03 merged to do anything: without the chat routes the sidebar says the chats could not be read.
2. **After P4-03 is merged, run the screen against it** as the test tenant: stop a reply, drop a stream, reload in the middle of a reply, and a turn that fails. A recorded turn that streams slowly, or a setting that slows the fake provider, would make the first three possible by hand. If `turns.md` gained entries under "Changed since the contract" after commit `5e781f7`, `src/api.ts` and `src/turns.ts` are the two files to change.
3. **Nothing in the server needs to change for this screen.** Three things would make it better, all for the chats lane:
   - Keep how long a thinking block took with the message, so "Thought for 6 seconds" survives a reload.
   - Say in `ChatReply` why a chat's last turn failed. Today only the page that watched the turn knows, and a reload loses the words.
   - `GET /api/v1/session` could say that the person is the test tenant, so the frame can mark it as test data, as `test-tenant.md` asks.
4. **The content security policy.** Still `default-src 'self'`, and the app needs nothing more. The composer sets its own height from script, which the policy allows. Do not add `'unsafe-inline'`.
5. **`tools/verify`, a standing check for `web/dist/`.** Still wanted (interface 001, item 4, and decision 0005). This branch rebuilt `web/dist/` by hand.
6. **The tokens need a shadow.** The composer and the menu use black at part strength, written in `src/chat.css`. A `shadow` token for each theme would take the last colour values out of the stylesheets. That is the design lane's file.
7. **`STATE.md`.** P4-04 is provisional. The line for the interface lane can read: next, the chat screen against the real routes, then edit, retry and the branch switcher.
