## What was done

- A new package, `internal/isolationdrill`. `Run` makes a throwaway folder with two invented people, starts the real server (`app.Open`) with the drill's own scripted model on the seam, a test MCP server that answers only the first person's token, an open one and the stand-in Google, fills the first person through the API with data of every kind (each piece carrying a marker word made for the run), and has the second person try every way in. It returns every attempt with its result. 342 tries in about six seconds:
  - **The session and the API** (226): every route that takes an id, with the first person's ids in the path, body and query (`pathValue`, `bodyFor`, `queryFor`); the second person's own chat or project with the first person's ids under it; the first person's message, upload, project file and model in the second person's turns; path tricks (raw and encoded `..`, `%2F`, `%5C`, the first person's tenant id and file hashes in file routes, artifact versions that climb out); uploads and project files named to climb into the first person's folder; forged and guessed ids; cookie and session swaps; models whose `ca_cert` names the first person's files; the share doors with forged, re-addressed and guessed tokens and the first person's upload; and sign-ins as the first person.
  - **Tools** (37): a turn whose model calls every tool a turn offers with the first person's ids, titles and hashes, the first person's connector tools by name, Gmail and Calendar; a model whose entry names the first person's key, and the first person's model by name.
  - **Jobs and agents** (70): a background task and a scheduled run doing the same, the built-in store's wiki compile job reading the first person's sources and answering with a page at their path citing their source, and the memory pass with the second person's memory space named as the first person's.
  - **Files on disk and the audit log**: the first person's folder hashed and their database compared row by row before and after each part; the second person's whole folder, database and vault searched for marks; both logs searched for tokens and keys; every API try checked in the second person's log under its request id, and every tool call too.
- The test `TestTheSecondPersonReachesNothing`, and the standing check `isolation drill` in `tools/verify/isolationdrill.go` (one line in `checks`), which makes `verify` 36 of 36.
- The fix for the hole the drill found: the settings routes take a model's `ca_cert` as PEM text only (`internal/settingsapi/cacert.go`, two lines in the add and replace handlers, `TestACACertPathIsRefusedThroughTheAPI`).
- Docs: `docs/architecture/isolation-drill.md` with every way tried and its result, decisions 0490 to 0492, rows in the overview and `internal/README.md`, a paragraph in `tools.md` and one in `settings-screens.md`.

## Findings

1. **A model's `ca_cert` path through the API. Medium, fixed.** `ca_cert` may be the path of a PEM file, the Chat Completions adapter reads it with the server's own rights, and `POST /api/v1/models` took any value. Any person could make Keystone read another person's file (`data/tenants/<id>/files/<hash>`; the ids are on the sign-in screen), `secrets.bin`, a device, or a share on another host, which Windows opens by signing in there as Keystone's account. Nothing came back to the person (the turn says only that the entry is refused, and the reason goes to the server's log), but the read happened. Now a path is refused through the API and set from the command line, and an edit that sends back the path an entry holds is taken, so the owner's gateway entry keeps working (decision 0490). Proven the drill catches it: with the check switched off by hand, the drill failed on it.
2. **A connector or model marked local may name any address on this machine or the home network. Low, not fixed: an owner question.** Every person on an install shares that network, so a server there that asks for no token, such as one person's notes server on `127.0.0.1`, can be added by another person as their own connector. Keystone sends each person only their own token, which the drill proves; a server that asks for one is safe.
3. **The audit log records a call's method and path, not its body or query. Low, by design.** A try with the first person's id in a body is in the second person's log by route, status and outcome, without the id. Bodies are left out because passwords and keys travel there (decision 0009).
4. **A sign-in for a person goes in their log and counts toward their wait, whoever sends it. Low, by design and known** (decision 0492; api.md already lists a limit on the door as not here yet).

## What was learned

- Everything a person keeps is reached through `c.Store`, given by the API shell from the session alone, and every in-memory map of the server is keyed by tenant and id. The drill found no way across in the routes, tools, jobs or doors; the one hole was a path the server reads with its own rights.
- Marks must never be typed by the second person: their own chats keep what they typed, and a search of their own chats would then look like a leak. The first person's names (`Lantern Accounts`, `Lantern Ledger`) are plain words the second person may use; only content carries marks. The same lesson for ids: a project file re-uploaded with the same bytes answered with the record of the first upload, whose name the second person had typed with the first person's id in it. Each file's bytes are now its own.
- The built-in store's ids count from 1 in each person's database, so `knowledge_read_source s1` reads the second person's own source. Short ids are never searched for; long ones only in API answers, before the second person's records hold any.
- The Operations sampler writes each person's snapshots on a timer, so the drill leaves `operations_snapshots` out of its comparison, with that reason in the code; nothing else of the first person's moved while the drill ran.

## For the owner

- **May a person add, from the browser, a connector or model marked local whose address is on this machine (`localhost`, `127.0.0.1`)?** Every person on the install shares this machine, so one person can reach another's server there if it asks for no token. Recommended: from the browser, local means a private address on the home network, and an address on this machine is set from the command line, as a connector that runs a program is (decision 0310).
