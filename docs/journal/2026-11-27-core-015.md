## What was done

- **The mark.** `tenant.Tenant` gains `admin`. `Install.SetAdmin` is its one writer and `go run ./tools/tenant admin <id> on|off [--yes]` its one caller; taking the last admin's mark is refused with a warning unless `--yes` is given. `Install.IsAdmin` and `Install.Marks` read `keystone.json` from disk every time, so a change from the command line counts in a running server at the next call. `save` now takes the marks from the file before it writes, so a server that read the registry before a change never writes the old mark back. A backup's manifest carries `admin` false, and a restore keeps the install's own mark. `tenant list` shows an `ADMIN` column. Decisions 0640 and 0641.
- **The step-up.** A migration adds `admin_until` to `signin_sessions`, and a second lets a passkey prompt have the purpose `step-up`. `signin.StepUp` checks the password through the function sign-in now shares (`checkPassword`), so wrong step-ups count towards the sign-in's wait; `BeginPasskeyStepUp` and `PasskeyStepUp` do the same with a passkey (`checkAssertion`, shared with `PasskeySignIn`). `admin_until` is now plus `admin.step_up_for` (15m, install), never past the session's end. `EndStepUp` closes it. `signin` also keeps `last_sign_in` in `tenant_meta` whenever a session opens, read by `LastSignIn`. Decisions 0643 and 0646.
- **The door.** `api.Route` gains `Admin` and `StepUp`; `api.Check` holds the `/api/v1/admin/` prefix and the `Admin` mark together. The shell's `who` reads the mark for a request to an admin path and records it with the actor `admin`; `adminDoor`, between `audit.Wrap` and the routes, refuses every path under the prefix, a route or not, with 403 `not_admin` without the mark and 401 `step_up` without a fresh step-up, except on the two `StepUp` routes. `Call.Admin` is true for a call that came through. `GET /api/v1/session` and the sign-in answer gain `admin` and `session.admin_until`. The OpenAPI document marks admin routes `x-keystone-admin` and step-up routes `x-keystone-step-up`. Decision 0642.
- **`internal/adminview`**, the only way an admin route reaches another person. It asks for the mark itself (`Asker`: the admin's id, the request id, the route), writes a `started` entry in the other person's log with the actor `admin:<id>` and what it is about to read before it opens anything of theirs, and an `ok` or `error` entry after; if the first cannot be written nothing is read. Today it has `People`. Decision 0644.
- **`internal/adminapi`**, the four routes, given the view and never the install: `POST /api/v1/admin/step-up` (password, or a passkey answer in the shape `PublicKeyCredential.toJSON()` gives), `POST /api/v1/admin/step-up/passkey` (a prompt in the shape `parseRequestOptionsFromJSON()` reads), `DELETE /api/v1/admin/step-up`, and `GET /api/v1/admin/people` (id, name, mark, added, last sign-in).

## What was learned

- The challenges table's CHECK named only `add` and `sign-in`; the first passkey step-up test found it. SQLite cannot change a CHECK, so the second migration makes the table again and carries the prompts in flight across. The first migration was already on the pushed branch, so it was not edited.
- The server reads `keystone.json` once and saves it whole. Until now nothing but the command line changed it while a server ran, so the old list in memory did no harm. A mark changed from the command line made that a security matter: a server's save (a keeper on first use, a restore) would have written an old mark back. The marks are now read from the file on every save. The same is still true of a tenant the command line adds while the server runs: the server's next save drops it. Nothing in the server saves today on a person's request, but P15-02 will (adding a person), so it must merge the tenant list from disk first.
- `usagereport`, `operations`, `jobs` and `schedules`, the packages that already sum a person's numbers, all reach forbidden packages through their own imports (`usagereport` through `knowledge/memory`; the rest through `turn`). The check proves it: with `usagereport` imported into `adminview` by hand it named `internal/adminview -> internal/usagereport -> internal/knowledge/memory -> internal/knowledge`, and with the import taken out it passed. So `adminview` can only read through narrow packages (`usage`, `tenantsettings`, `signin`, `audit`) or its own queries.
- Writing every read in the other person's log, as the spec asks, means a list of N people writes 2(N-1) entries. The audit log already grows by far more than that per turn (core 014, finding 4).
- The walks of the other checks (`tenant isolation`, `calls recorded`, `no keys in output`, the isolation drill) needed no change: their callers carry no mark, so every admin route answers 403 and is recorded, which is what each of them wants.

## Provisional, and why

The whole item, on A1 and A2. If the owner answers that an admin is a separate account (A1), the mark becomes that account's flag and the step-up stays; the door, the routes and the audit entries keep their shape. If he widens what an admin may see (A2), only `adminview` and the deny list change, and widening it would break fixed rule 1, which the brief marks as hard to reverse.

## Questions, each with a recommended answer

1. **How often may the Admin → People screen read the list?** Every read writes two entries in every other person's audit log, as the spec asks. Recommended: on opening the screen and on a refresh button, never on a timer. Built: nothing polls; the screen is P15-02's.
2. **A tenant the command line adds while the server runs is dropped from `keystone.json` by the server's next save.** This was so before this item, and decision 0641 names it. Recommended: P15-02, which adds people from the server, merges the tenant list from disk on every save, as `save` now merges the marks, and serves a person added on disk without a restart. Built: the marks only.
3. **An admin with no password, who signs in by passkey only, while `signin.passkeys` is off, cannot step up.** Passkey sign-in has no route yet, so no such admin exists today. Recommended: leave it; when passkey sign-in gets its routes (P4-01), the step-up's passkey route is already there behind the same setting. Built: as recommended.
4. **Should taking the last admin's mark need anything more than `--yes`?** Recommended: no; whoever runs the command line owns the data folder and can mark another admin the same way. Built: `--yes`.
