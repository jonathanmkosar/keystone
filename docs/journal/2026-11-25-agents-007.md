## What was learned

- MCP's tool annotations cannot carry what a send needs: whether this one call reaches other people, and the card's exact words. Tools written in Go behind the connector registry carry both as functions of the input, and reuse everything P7-04 built (decision 0350).
- "Always asks" cannot be a flag per tool: a calendar change asks by policy when only the person is on the event and always when guests are. It is a function of the input, held in `Decide` and again where the tool runs (decision 0351). With `Decide` weakened, the `verify` step saw the invitation refused by the second guard instead of run.
- Whether an event has guests is a fact about the event, not the input, so the rule alone could be fooled by a call that leaves them out. The call names the title and guests, and is checked against the live event before it changes anything; a call that left them out changes nothing and is told whom to name (decision 0353).
- The session cookie is SameSite=Strict, so a browser coming back from Google does not send it. Google returns to a page, which posts the code with the session it has; no door route was needed, and the code never enters the API's audit path (decision 0352).
- Install-scope settings have no override store yet: the server reads the shipped defaults. So the OAuth client's id is a tenant-admin setting, written for each person with `tools/tenant setting set`, and its secret goes in each person's vault.
- SQLite cannot change a CHECK in place. Making the children against the new parent and dropping the old children first lets the rebuild run inside the migration's transaction with foreign keys on; renaming the new parent rewrites its children's references.

The item's proof:

- **Drafting and sending an email needs approval.** In `go test ./internal/turn` and in `calls recorded` on the real server: the draft asks (by policy in a fresh chat, with the reason `outside` after the search), the send asks with the reason `others`, nothing reaches the stand-in while they wait, and both run once approved; the send's card names the recipient, the subject and the words, and the reply joins the thread.
- **A send set to always still asks**, declined is not sent, approved is.
- **Personal calendar changes follow the policy**: an event with no guests asks at its default and runs without asking set to always.
- **A guest-notifying change always asks**: an invitation set to always asks with `others` and is sent with `sendUpdates=all`; an update set to always that leaves out the event's guests changes nothing.
- **Tokens never appear in output**: not in any event, route answer, audit entry, kept problem or file, with a stand-in that repeats the refresh token everywhere (`no keys in output`).
- In a browser, on a server built from this branch by a harness (not committed) on port 7993 with a data folder inside the worktree, signed in as the test tenant with the fixture's password, and the stand-in on port 7994 consenting at once: Connect Google went to the stand-in and came back through `/settings/connectors/google` to "Connected as person.one@example.com", with the address bar cleared; the recorded Gmail turn asked for the draft and then the send (set to always), each card one fact to a line, and sent once approved; the personal event ran without asking; the invitation asked and "Not now" declined it; Disconnect cleared it. Dark, phone width, and the not-set-up section after a restart with no client. The console's only error was the sign-in probe's 401. The harness and the data folder were removed.
