## What was learned

- The item's proof asks that every overridable setting has a control. With a generated screen that is a fact about the route, and it can be tested in Go on the real registry with no browser. The test also stores and resets each setting, which found nothing wrong and would find a setting whose own default it refuses.
- The four packages underneath each guard a fixed rule and may not read a setting. A package above them reads the two values they need and passes them in. Nothing in them changed.
- The `offline` check lists the folders that may import `net/http`. A package of route handlers has to be on it, as `internal/turn` is.
- The OpenAPI builder does not flatten an embedded struct. A model's row is `{"entry": {...}, "key_present": ...}` for that reason, and it reads better.
- The registry's errors and the vault's are written so they never repeat a value. The routes add their own words for a bad secret name and a bad setting value all the same, because `tenantsettings` and the vault do quote what they were sent.
- The audit log keeps a call's path and never its body, so `PUT /api/v1/secrets/provider.one` leaves the name in the log and not the key. Nothing had to be added for that.
- A row of tabs that scrolls sideways grows a vertical scrollbar if a tab hangs one pixel below it. Found in the browser and fixed.

## For the owner

1. **May a person see the settings that are the admin's to change?** They can: General lists all 66 under "Set for the whole install", read-only, and none holds a secret. Some say how the install is set up, such as the data folder and the address it listens on. Recommended: keep them visible to the admin, and show a person only the ones that explain something they can see, once there is an admin role. Assumed meanwhile: everyone sees all of them. Nothing waits on the answer.
2. **May a person mark their own model trusted?** This is the open question on the model registry, and it now has a screen. A person can add a model on any address and mark it trusted, and it may then read their sensitive spaces. Recommended, as before: the admin only. Until there is an admin, the person on a one-person install is the admin, so nothing is lost.
3. **A short name.** The greeting still uses the whole name (interface 002). Profile shows the name and cannot change it: a person's name is in the install's registry, which the server reads once at start. Recommended: a "what to call you" setting in the interface lane, which General would draw with no other work.
