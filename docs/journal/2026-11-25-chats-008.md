## What was done

- **The record** (`internal/attach`, migration `20261125T195300_chat_attachments.sql`). One row for each chat attached to a chat; `handoff = 1` on the row that says a chat continues from another, at most one per chat. Both ends refer to the tenant's own `chats` with `ON DELETE CASCADE`, so fixed rule 1 holds by construction and the rows go with either chat. `Add`, `Remove`, `Handoff`, `List` (the parent first), `Handoffs`, `Is`. The package reads no setting and does not import the chat record, and is a guard of rule 3 in `fixed rules`.
- **The rules** (`attach.MayShow`). A sensitive attached chat (held, or its recap marked) reaches a call only when every model of the call's route may read it, and the chat it goes into is held first; otherwise it is left out and a pinned line says how many, with no name. An incognito chat is neither attached, nor attaches, nor is handed off, and one made incognito later is left out (decision 0361). As recall's items do, a sensitive attached chat holds the route when the chat's own model may read it: one added line in `Runner.sensitive` (decision 0363).
- **Into each call** (`internal/turn/attach.go`). `Runner.build` fills `contextbuild.Input.Attached`: each attached chat as its title, id, last date and recap, the parent pinned. In the first call of a turn, a missing or stale recap is made by `makeRecap` under the turn's request id, waiting up to `chats.attached_summary_wait`, also for one being made already (decision 0360). Three added lines in `context.go`; `contextbuild` itself did not change.
- **`open_attached_chat`**, offered while the chat carries a chat that is not incognito: a page of the attached chat's branch, oldest first, at most `chats.attached_page_messages` messages and `chats.attached_page_max_chars` characters, with tool results and thinking left out so the result is Keystone's own content. Made for each call for the least of its route and kept with the past-chat tools, so it runs through a registry of its own and is recorded as every tool call is; a turn resumed after an approval makes it again (one added line in `approvals.go`).
- **Handoff.** `POST /chats/{id}/handoff` makes a fresh chat with the parent attached as `handoff`, and names the model the parent would use next (decision 0362). The routes: `GET /chats/{id}/attached`, `PUT` and `DELETE /chats/{id}/attached/{other}`, listed in `internal/app`. `docs/api/openapi.json` regenerated.
- **The screen**, provisional: chips over the composer (parent copper and fixed, `sensitive` and `incognito` marks, a button to take one off), "Attach a chat" with a picker filtered by title and summary, and at the right of the header "Continued from", "Continued in" and **Hand off**, which opens the new chat with the parent's model picked. New files `AttachedChats.tsx`, `ChatLinks.tsx`, `attached.ts`, `attach.css`; added lines in `Chat.tsx`, `Shell.tsx`, `api.ts` and `Icon.tsx`. `web/dist/` was built to look at it and not committed.

## What was learned

- The item was mostly joining what was there: `PartAttached` and its share were waiting in the builder, `makeRecap` writes a recap for any chat, `recap.Sensitive` and `MayShow` already answered rule 3 for another chat, and the past-chat tools showed how to make a tool for each call. The new code is the links, the text and the pages.
- The first version of the sensitive test passed with the routing line switched off: with no fallback chain, a local pick's route is the local model either way. Giving the person a hosted fallback made the line matter, and the test caught its removal. A test that cannot fail for the line it is about proves nothing; each fault was put in by hand to find that out.
- The tool's refusal named the attached chat's id when the model had not given one, which told a hosted model which chat was left out. The past-chat search names no chat it leaves out, so the tool now names none either.
- Holding the chat only when the tool reads a sensitive chat would have missed a call that carried it in the context alone. The test sends a plain question on the local model too, and the chat must be held.
- gofmt lines up trailing comments in a block, so a longer line added to a block of aligned comments changes every line in it. The added lines were shaped to fit inside the existing blocks, or given comments of their own, so every shared file shows added lines only. One planned addition, listing the tool on Settings → Approvals, was dropped because an existing test lists the tools exactly.
- A tool that answers with an earlier chat's tool results would hand outside content to a call as inside content, and so let a side effect run without asking (fixed rule 2). Leaving results out, as `read_chat` does, keeps the tool honest at the cost of what only a tool found.
