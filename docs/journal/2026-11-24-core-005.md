# Core 005, 2026-11-24

Item done: P2-02, sign-in and sessions.

## What was done

- A new package, `internal/signin`, with plain data and functions. It works on one tenant's store handle, and everything it keeps is in that tenant's own database. Standard library only.
- Passwords: `SetPassword`, `HasPassword` and `SignIn`. A salted PBKDF2-SHA-256 hash from `crypto/pbkdf2`. After a few wrong passwords in a row, password sign-in waits.
- Sessions: `Check`, `Resolve`, `TenantOf`, `SignOut` and `SignOutAll`. A token names its tenant and is stored only as its SHA-256. `Resolve` turns a token into the one tenant's store. It is the function P2-05 calls on every route.
- Passkeys: `BeginAddPasskey`, `AddPasskey`, `BeginPasskeySignIn`, `PasskeySignIn`, `Passkeys` and `RemovePasskey`. The server side of WebAuthn with no new module. They were not split into another item.
- One migration, `20261124T210000_sign_in.sql`, with four tables: `signin_password`, `signin_sessions`, `signin_passkeys` and `signin_challenges`.
- `go run ./tools/tenant password <tenant-id>` gives a person a password, read from standard input.
- A new standing check in `verify`, `tenant isolation`, in `tools/verify/isolation.go`.
- Nine settings under `signin.` in `settings/core.json`.
- Docs: `docs/architecture/signin.md`, a row in the overview, decisions 0007 and 0012, the tenant command and the new check in `tools.md`, and a section in the runbook for adding a tenant.

## What was learned

- The plan says a tenant and a user are the same, so there is no table of users and no user name. A tenant has one password at most. The cost shows up one step later: with no shared list of names, a sign-in route must be told which tenant is signing in before it can check anything. That is the question for the owner below.
- A session has to find its database from the token alone, and no database may hold rows from two tenants. So the token names its tenant (decision 0007). The name is a claim. The proof is the token's hash in that tenant's database, and the hash covers the name, so rewriting the name breaks it.
- That alone already refused tenant A's token on tenant B's store. The case it did not cover was A's session row ending up in B's database. `Check` now refuses a token that names another tenant before it reads anything. Taking that test out makes one test and the new `verify` check fail, so both are known to look at it.
- WebAuthn needs no CBOR reader if the page sends `getPublicKey()` and `getAuthenticatorData()` beside the usual fields (decision 0012). The key arrives in a form `crypto/x509` reads, and the part of the authenticator data the server needs is fixed-size fields.
- The user handle a passkey gives back is not covered by its signature. It is still worth checking, as a second test: it is what refuses A's passkey row copied into B's database.
- Counting a password try before checking it, in one `UPDATE`, means tries made at the same moment cannot pass the limit together. The count is cleared by a good sign-in.
- 600,000 rounds of PBKDF2-SHA-256 take under a tenth of a second on this machine, so `verify` and the tenant command use the shipped settings. The package's own tests use 50 rounds.
- Windows PowerShell 5 as it comes pipes text as US-ASCII. A piped password with an accent in it arrives with a question mark in its place. This was seen with `$OutputEncoding` set to ASCII, which is the stock value. The runbook says so.
- From the WebAuthn rules, not from trying it: a browser allows passkeys on `localhost` or over HTTPS, and not on `127.0.0.1`, which is what `keystone serve` prints. `signin.passkey_origin` ships as `http://localhost:7900`.

## Provisional

The item is done. Two things in it are held back or rough.

- **Passkeys are off.** `signin.passkeys` ships as false. The test authenticator builds its answers from the WebAuthn rules, so a misreading of the rules would be in the code and in the test alike. P4-01 builds the sign-in screen and proves the exchange in a browser, then the setting goes on. The page must send `getPublicKey()` and `getAuthenticatorData()`, ask for user verification, and ask for a passkey that holds the user id.
- **A typed password shows on the screen.** The standard library cannot switch a console's echo off. `golang.org/x/term` can, and would be a second outside module, so it was left out. Recommended: add it in P2-05, when the command-line client is built and needs it too.
