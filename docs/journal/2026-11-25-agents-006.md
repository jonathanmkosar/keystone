# Agents 006, 2026-11-25

Item done: P8-03, scheduled tasks. A person makes a schedule (hourly, daily, weekdays, weekly on chosen days, or once) in their own time zone; each run is a background task working in a chat of its own, titled by the schedule and the date, so the run is a chat with its result as the reply; a run missed while Keystone was not running happens once when it is back, marked late; a switch holds every schedule. The item has no owner gate; the Scheduled screen follows a draft mockup and is provisional on the agent mockups (P1-05) for its look.

Built in its own worktree on `agents/p8-03-scheduled-tasks`, while connectors (P7-04), chat summaries and past-chat search (P5-05) and prompt caching (P5-03) were built in others.

## What was done

- A new package, `internal/schedules`:
  - A schedule and its runs are rows in `schedules` and `schedule_runs`, from one migration, `20261125T180000_schedules.sql`.
  - `Next(recurrence, after, zone)` works out the next due time from wall-clock time in the person's zone, with written rules for the changes of the clocks: a skipped time runs as far into the new hour as it was into the old, a doubled time runs once at the first, hourly counts real hours. The zone database is compiled in (`time/tzdata`).
  - `Scheduler`: a goroutine under the turn runner that looks at once when the server starts, then every `agents.schedule_poll` or sooner. A due schedule gets one run standing for every due time that passed, its next due time moved past now in the same transaction that writes the run; a unique index refuses a second run for one due time. A run is started in steps that can be repeated: the row, then a chat titled by the schedule and the date (incognito when the schedule is), then a background task in that chat.
  - The person's zone is the new tenant setting `agents.time_zone`, and their switch is `agents.schedules_paused`; five install settings besides, in `settings/agents.json`.
  - Ten routes under `/schedules`: list, create, read with runs, edit, delete, pause, resume, run now, pause all, resume all.

## What was learned

- Background tasks already were unattended chat turns with recovery, a budget and approvals that wait. A run built on them is a chat with no new runner, and the only thing missing was a task whose work chat and "from" chat are the same one: a hundred lines in a new file, and five lines in the task runner (decision 0340).
- "A missed run happens once" holds across a crash only if moving the next due time and writing the run are one transaction. A mutation that left the next due time behind was still stopped at one run by the unique index on the schedule and the due time: the database's own "once" is worth keeping as a second guard (decision 0341).
- Go's `time.Date` does not promise which instant it picks for a wall time the clocks skip or repeat, so the rules are written out and tested in New York and Lisbon both ways. Windows has no zone database, so without `time/tzdata` a binary on a machine with no Go installed cannot load `Europe/Lisbon` at all (decision 0342).
- Sending due times in the person's zone, so the JSON carries the offset, lets the screen show the person's clock from the text alone, whatever the browser's zone, which on a phone away from home may not be the person's.
- New Keystone's routines had the right idea for catch-ups (the latest slot at or before now, run once) and for not running a routine while its last run is busy. Its slot-hash request ids are replaced here by the unique index.
- The verify check first read a run's status before its task's note was confirmed, and once caught the run as still running: a run is read again once its task has ended.
