# Models 005, 2026-11-24

Item: P3-05, the OpenAI Responses adapter. Provisional, on the owner gate. Begun on November 24 and finished on November 25.

## What was done

- A new package, `internal/adapters/responses`: a `seam.Provider` for one registry entry that speaks the OpenAI Responses API over HTTP, with the standard library and no SDK. It posts to the entry's endpoint with `/responses` added and reads the reply as server-sent events.
- The request: system text as `instructions`; text, images and files in a user message; function calls and their outputs as items of their own; function tools; the output limit, capped by the entry's.
- The stream: text, refusals, function calls and reasoning folded into the seam's blocks, one open at a time. Usage is split so cached input is not counted twice.
- Reasoning: nothing is stored at the provider, so encrypted reasoning comes back, is kept in the thinking block's signature, and goes back on the next call (decision 0110). A thinking budget becomes low, medium or high effort by two settings (decision 0111).
- Errors: a status, an `error` event and a failed response each become a `seam.Error` with a kind and whether it may be retried.
- Retries: a call is sent again only while nothing of its reply has been passed on, with a wait that doubles and honours `Retry-After` (decision 0112).
- `adapters.Responses(options)`, the builder, in `internal/adapters/responses.go`.
- Seven settings under `responses.` in `settings/models.json`.
- `fixtures/responses-adapter/`: 21 invented exchanges in five files, with a README.
- The folder is on the `offline` check's list, and has a line in `verify`'s list of parts.
- The doc `docs/architecture/adapter-responses.md`, a row and three decision links in the overview, a row in `internal/README.md`, and a paragraph in `tools.md`.

## What was learned

- The fixtures are not recordings. With no key and no network there was nothing to record, so they were written by hand from what is known of the public API. They prove the adapter does what its author believes the API does. They cannot prove the belief. The doc has a "Sure and inferred" list for that reason, and the fixtures' README says the same.
- The seam's thinking signature was enough to carry this provider's encrypted reasoning without a change to the seam. It needed a prefix, so that a signature from another adapter is recognised and left out, not sent to a provider that would refuse it.
- The Responses API has no thinking budget and no way to switch reasoning off that every model accepts. A budget of zero can only mean "send no reasoning field".
- Holding back the seam's `start` event until the first block makes a reply that fails straight after it was created invisible to the caller, so it can be retried. Sending `start` when the provider says "created" would have made every such failure the caller's.
- A provider's message for a refused key repeats part of the key. The adapter drops that message and gives its own, and still replaces the whole key in every other message.
- `tools/verify` may not import a network package, so the `no keys in output` check cannot run a replay server. The looking for the key is in the adapter's own tests.
- A JSON settings file cannot take a new last entry without a comma on the line before it. That is the one existing line changed in a shared file.
- A new line in a `gofmt`-aligned map moves the lines beside it. A blank line before the new one starts a new group and leaves the old lines alone.
- The worktree for this loop was again cut from the Python `main`. The branch `models/p3-05-responses-adapter` was made from `reboot` at `2d050fe` before any work.

## What was verified

On Windows 11 with Go 1.26: `gofmt -l .` prints nothing, and `go run ./tools/verify` is 13 of 13.

- Each of the 21 exchanges: the path, the header and the body sent, the number of calls made, and the whole reply through the seam's collector or the error's kind and whether it may be retried.
- The invented key is in no event and no error of any exchange, including two where the server repeats it, and in no printing of the provider.
- A busy provider and a rate limit with a short wait are retried and the caller sees one reply. Three failures in a row give up. A wait of thirty seconds is not sat through.
- Cancelling stops the stream with the context's error. A stream that goes silent is given up on. An error from `emit` ends the call with that error.
- A request the adapter refuses never reaches the endpoint.

Not run: macOS and Linux. **Nothing here has spoken to the real API.**

- **The live check.** The item's owner gate. It needs an OpenAI key and a network. Until it is run, every "inferred" line in the doc is unproven, and the adapter should not be the only model a person relies on.
