# Core 006, 2026-11-24

Item done: P2-03, per-tenant secrets.

The lane's session built and committed the code in its own worktree and then stopped. This entry, the doc, decision 0008 and the runbook were written by the integrator at the merge, from the code and the item's plan.

## What was done

- A new package, `internal/secrets`. A `Vault` is one tenant's `secrets.bin`: set, get, list names, delete. A `Keeper` stands for the install master key and wraps each tenant's data key.
- Keepers: DPAPI on Windows, the login keychain on macOS, the Secret Service on Linux, a key file for a machine with none, and one held in memory for tests.
- `internal/tenant/secrets.go` joins the two. `Store.Secrets()` returns the tenant's vault. The keeper is found the first time a secret is used, and `keystone.json` then records which keeper it is.
- `go run ./tools/tenant secret set | list | delete`. A value is read from standard input and never printed.
- A new standing check in `verify`, `no keys in output`, in `tools/verify/nokeys.go`.
- One setting, `secrets.keeper`, in `settings/core.json`.
- Docs: `docs/architecture/secrets.md`, a row in the overview, decision 0008, the command and the check in `tools.md`, and `docs/runbooks/secrets.md`.

## What was learned

- Two lanes can each be green alone and red together. P2-03 had `internal/tenant` read the `secrets.keeper` setting. P2-04 added a check that the package guarding tenant isolation cannot read any setting. Neither worktree saw the other. The merge did, and `verify` failed on it.
- The fix was in the code and not in the check. `internal/tenant` now takes the keeper's name from its caller through `Install.NewInstallKeeper`, and the tenant command reads the setting. An install that has no master key and has been told nothing refuses to store a secret, with a message that says so.
- The key stores on macOS and Linux can be reached through a command each system already has, so no outside module and no C compiler is needed (decision 0008).
- Finding the keeper on first use, and not when the data folder opens, means `rebuild`, `verify` and every test that stores no secret never touch the key store.

## What was verified

On Windows 11 with Go 1.26.0, on `reboot` after the merge:

- `gofmt -l` prints nothing, `go vet ./...` is clean, and `go test ./...` passes.
- `go run ./tools/verify`: 12 of 12.
- The item's proof, in the package's tests: `secrets.bin` does not hold the plain value, another master key cannot read it, one tenant's file is refused in another tenant's folder, and a damaged file is refused and left as it is.
- The DPAPI keeper, in a Windows-only test: a secret is stored, `keystone.json` records `dpapi`, and the secret reads back after the folder is opened again.

Not run:

- The keychain keeper on a Mac and the Secret Service keeper on Linux.
- The tenant command's `secret` commands by hand. Their tests pass.

## Provisional

The item is done. The macOS and Linux keepers are provisional until they have run on those systems.
