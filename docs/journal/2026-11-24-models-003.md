# Models 003, 2026-11-24

Item done: P3-02, the model registry.

## What was done

- A new package, `internal/models`: the registry. A `Model` is one entry: name, label, adapter, endpoint, the provider's own name for the model, the name of the secret that holds its key, context window, output limit, capabilities, price and class. `Check` refuses an entry that is not valid and gives the reason. `Decode` and `Encode` read and write one as JSON.
- Each tenant's entries are rows in a `models` table in its own database: `Add`, `Replace`, `Remove`, `Get`, `List` and `Usable`. An entry is checked before it is stored and again each time it is read.
- `Model.MayReadSensitive()`, the one place a class becomes yes or no for fixed rule 3. The package is listed as a guard for `rules.sensitive_content` in the `fixed rules` check, and imports only the tenant store and the standard library.
- `Price.CostMicros`, which turns the seam's four token counts into the audit log's unit.
- A new package, `internal/adapters`: `Open` turns a tenant's entry into a `seam.Provider`, with the key read by name from the tenant's vault. `Fake` gives the set of builders that holds the fake. `Limits` reads the one setting.
- A setting, `models.max_per_tenant`, default 50.
- `fixtures/models/`: six example entries that between them use every adapter and every class, and 25 refused entries, each with its reason.
- A surface for the registry in the `no keys in output` check, `tools/verify/models.go`.
- The doc `docs/architecture/models.md`, two rows in the overview, lines in `verify`'s list of parts and in `internal/README.md`, a paragraph in `tools.md`, and decisions 0050, 0051 and 0052.

## What was learned

- "Adding a model is a settings change" does not fit the settings registry, which holds one text value for one key that is compiled in. It is read here as a change to stored data with no change to code. Decision 0050.
- The registry does not stop a call, and it is still part of rule 3: the rule's words are "models the registry marks". So the package that reads the mark is a guard, and cannot read a setting. That pushed the provider code into a second package, because the fake reads settings and the real adapters will open connections. Decision 0051 and 0052.
- A guard cannot take a list from settings without letting a setting widen the rule. The names that count as the home network are therefore fixed in code, which is the one place this item goes against "a value someone might change is a setting". `trusted` is the way through for any other name.
- The places a key gets pasted by mistake are the `key` field and the endpoint's user, password and query. A refusal never repeats either field.
- A trailing comment on one line of `fixedRuleGuards` makes `gofmt` move the comment on the line above it. The new line has no comment, so one line changed and no other.
- The worktree for this loop was again cut from the Python `main`. The branch `models/p3-02-model-registry` was made from `reboot` at `8b85a3a` before any work.

## What was verified

On Windows 11 with Go 1.26.0: `gofmt -l .` prints nothing, `go vet ./...` is clean, and `go run ./tools/verify` is 12 of 12.

- Every example entry is accepted and comes back the same from JSON. Every refused entry is refused for the reason its fixture gives.
- A model added to one tenant is there after its database is reopened, and is not in another tenant's registry.
- Rows written straight into the table are refused when read: a hosted address marked `local`, an entry under another name, text that is not JSON, and an entry with a `trusted` field.
- A model added to a tenant's registry is opened and answers a call through the fake, with no change to code.
- A key reaches a builder from the vault and not from an environment variable. A missing secret is refused by name. A builder's error with the key in it comes out without it.

Not run: macOS and Linux. No real adapter exists, so nothing here has spoken to a provider.

## Question for the owner

**Who may add, change and remove models in a person's registry: the admin only, or the person too?**

Recommended: the admin only. A model's class decides whether it may be sent content from a sensitive space, so marking a model `trusted` is a security choice, and it should sit with whoever runs the install. Each person picks among the models they have been given, and still keeps their own keys in their own vault.

Assumed meanwhile: nothing. The registry's functions take no role, so the route that calls them decides, and either answer fits without a change here. It holds up nothing built. It shapes the registry routes and the models screen in P11-01.
