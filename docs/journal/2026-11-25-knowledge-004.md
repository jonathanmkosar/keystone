## What was done

- A new package, `internal/knowledge/personmap`. It imports the knowledge interface and the tenant handle and nothing else of Keystone's. No network, no setting.
- The profile: one text for each tenant, with `ReadProfile` and `SetProfile`. An empty text clears it, and a text over the limit is refused.
- The map: an outline made from `Store.Catalog`, one line for each space with its page count, its kinds with their counts, and a few titles. `Build` makes it from a catalog, and `Load` keeps it in the tenant's database and builds it again when the store's marker has changed, or the catalog's hash where the store has no marker.
- Two versions of the map for fixed rule 3. `Map.Text(mayReadSensitive bool)` is the only way to either. The open version holds nothing from a sensitive space but the number of spaces held back.
- `ForContext`, one call shaped for the context builder's slot. It returns the profile and the map for one model, each with an estimate in tokens.
- One migration, `20261125T060000_person_profile_and_map.sql`: `person_profile` and `person_map`, one row each at most.
- Settings: `knowledge.profile_max_chars`, `knowledge.map_max_tokens`, `knowledge.map_titles_per_kind` and `knowledge.map_title_max_chars`. The package reads none of them. The caller does, and passes `Limits`.
- `tools/verify`: the package joins `fixedRuleGuards` for `rules.sensitive_content`, through an added `init`, and `componentDocs`.
- Docs: `docs/architecture/knowledge-profile-and-map.md`, a row in the overview and in `internal/README.md`, a pointer in `knowledge.md`, and decisions 0180 to 0183.

## What was learned

- The name of a space is content, and so is a kind. The first thought was to list a sensitive space by name with its titles removed. A space called after an illness says the thing the label is there to keep in. The open version now leaves the whole line out (decision 0181).
- A kept map and "labels are read fresh" pull against each other. The kept open version is safe only because the marker, read on this call, promises no label has changed. When the store is down nothing promises that, so the kept map is not used, for either kind of model (decision 0182).
- The order of the two reads matters, as it did for the Waymarks labels. Marker first, catalog second: a change between them costs one extra build. The other order could keep an old map under a new key and never notice.
- The package cannot count tokens as a model does, because a guard of a fixed rule may not read a setting and the budget package reads settings. The budget's estimate for plain text is one line of arithmetic, so the caller passes `budget.chars_per_token` in and the package does the same sum.
- `fixedRuleGuards` is a map written in one literal, so a second package for a rule cannot be added without changing a line. An `init` that appends to it adds lines only, and the check and its tests read the map after `init` has run.
- The docs check does not follow links, as knowledge 001 noted. The component doc was committed one commit before the four decision records it links to.

## What was verified

- `go test ./internal/knowledge/personmap`, against the built-in store, `none`, and a small store with no capability written in the test:
  - The item's proof. With four invented spaces in the built-in store, the map names every space, every kind and every title, and its estimate is under the default limit of 600 tokens.
  - Nothing from a sensitive space is in the open version. A space made sensitive is gone from it at the next call, and comes back when made normal.
  - A blank label, an unknown label, and one unlabelled entry among labelled ones each make the space sensitive.

  - A store with no marker builds again only when its catalog or a label changes.

   Recommended: yes. One line, a number and no names. Without it a hosted model says the store holds nothing on a subject when the truth is that it may not look, and the person has no cue to switch to a local model.

## For the integrator

- The call for the context builder's slot, once per turn, after the model is chosen:

      p, err := personmap.ForContext(ctx, tenantStore, knowledgeStore, model.MayReadSensitive(), limits)

  `tenantStore` is the tenant's `*tenant.Store`. `knowledgeStore` is what `knowledge.Open(ctx, adapterName, tenantStore)` returned for the tenant's `knowledge.adapter`, or nil. `p.Profile` and `p.Map` are the two texts, either of which may be empty, and `p.ProfileTokens` and `p.MapTokens` their estimates. Neither text has a heading: the builder says what each is. `p.WithheldSpaces` and `p.StoreErr` are for the turn inspector. An error from the call is the tenant's database, the limits or the context, and should fail the turn as any database error does. A store that is down is not an error.
- `limits` is a `personmap.Limits` the caller fills from settings: `ProfileMaxChars` from `knowledge.profile_max_chars`, `MapMaxTokens` from `knowledge.map_max_tokens`, `TitlesPerKind` from `knowledge.map_titles_per_kind`, `TitleMaxChars` from `knowledge.map_title_max_chars`, and `CharsPerToken` from `budget.chars_per_token`, which is `budget.Options.CharsPerToken` if the caller already holds the budget's options. The keys are constants in the package. The package itself must never import `settings` or `internal/tenantsettings`: `verify` refuses it.
- For a test tenant on the fake provider, pass false unless the entry's class says otherwise. The zero answer is the safe one.
- Nothing calls `knowledge.Open` in the server yet. Whoever opens the store for a turn should open it once for the turn and pass the same handle to `ForContext` and, later, to recall.
- The migration is stamped `20261125T060000`, later than every one on `reboot` at 1318039. If another lane's migration lands with a later stamp, nothing needs to change: the two tables stand alone.
- No existing line was changed in a shared file. `docs/architecture/overview.md`, `internal/README.md`, `tools/verify/main.go` and `tools/verify/fixedrules.go` each gained lines. `settings/knowledge.json` and `knowledge.md` are the lane's own.
