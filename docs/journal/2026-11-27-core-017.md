## What was done

- **The keys.** `secrets.Vault.Subkey(purpose)`: HKDF-SHA-256 of the person's data key for one named purpose, bound to the tenant id, making the data key and an empty `secrets.bin` for a person with none. The data key still never leaves `internal/secrets` (decision 0261). `atrest.Derive` makes the pages, files and names keys from the subkey for "keystone at rest v1"; `tenant.Install` keeps them per person once unwrapped.
- **The database** (decision 0660). A new package, `internal/atrest`, registers one VFS with the driver Keystone already has (`modernc.org/sqlite/vfs.Register`, v1.63.0): no new module, no cgo. It opens `keystone.db` and `keystone.db-journal` only, only in a folder given keys, and keeps them as page files: a header (magic, salt, key check) and a slot per 4096-byte block, AES-256-GCM under a key per write (from the file's key and half the nonce), bound to the tenant id, the block's place and its length. Temporary files stay in memory (the driver's own). A sealed database uses `journal_mode=truncate` and `synchronous=full`: the driver's VFS has no shared memory, so no write-ahead log. A torn block is an error in the database and zeros in the journal. The VFS keeps one handle per file for the whole process, owned by a hold that locks the file against other processes (`LockFileEx` far past the end, or `flock`), waiting `encryption.lock_wait`.
- **Files** (decisions 0661, 0662). `Store.FilesFolder()` and `Store.ArtifactsFolder()` return a `tenant.Folder` with `os.Root`'s methods; for a sealed person it seals each file whole in 64 KiB chunks under a key of its own (salt in the header, counter nonce, last-chunk flag, header and tenant id as additional data) and names every part of a path by a keyed hash; for a plain person it passes through.
- **A sealed folder** holds `seal.json` (format, tenant id, key check). `openFolderDB` opens through the VFS or as before, and refuses a folder whose database and `seal.json` disagree.
- **The first start** (decision 0663). `Install.SealAll`, called by `keystone serve` (`cmd/keystone/atrest.go`) before it serves: for each plain person, a P13-04 backup under a random passphrase wrapped by the master key beside it, read back; a sealed copy in `tenants/.<id>.sealing/` (`VACUUM INTO` through the VFS, files sealed); read back (integrity check, every table's rows counted and hashed with rowids on both sides, every file opened and hashed), synced, `seal.json` last; the plain folder renamed aside and the copy into place, opened and checked there, the plain one put back if not; only then the plain folder removed. A failure leaves the person plain, stops the run, is logged by id, and the server starts. `Install.recover`, run by `tenant.Open` for every person, finishes or undoes a sealing a stop cut short. `Install.Create` seals a new person at once.
- **Backup and restore** (decision 0664). A sealed person's snapshot is written through the VFS under the same keys and carried sealed; a restore opens the folder with the keys from its own secrets file before placing it, and forgets the keys it kept for a replaced person.
- **The command.** `go run ./tools/tenant encryption status | passphrase <backup file>`.
- **Settings** in `settings/core.json`: `encryption.at_rest` (true), `encryption.lock_wait` (30s), `encryption.backup_folder` (backups/before-encryption), all install.
- **The check** `encryption at rest`, the 48th, in `tools/verify/encryption.go`.
- **The load test** runs with encryption on, as it ships: the rig turns it on from the setting, and counts the files' and artifacts' sizes as they are on disk (`atrest.SealedSize`).
- **Other lanes, at the point where bytes are written and read.** The chats lane's `internal/uploads/uploads.go` (8 lines) and `internal/chat/chat.go` (2 lines), the projects lane's `internal/projects/blobs.go` (6 lines) and the agents lane's `internal/artifacts/artifacts.go` (8 lines) changed `s.Files()` to `s.FilesFolder()` and `s.Artifacts()` to `s.ArtifactsFolder()` on the lines that write, read, stat, rename and remove a person's files, and nothing else.

## What was learned

- `modernc.org/sqlite` v1.63.0 has a read-write VFS for Go code (`vfs.Register`). It has no shared memory and no lock between processes, and reports no device characteristics, so SQLite closes a truncate-mode journal at the end of every transaction. On Windows an open takes about a millisecond, more with the virus scanner: the first version opened the journal at every transaction and the database at every connection, and streamed a reply in 0.9 s to 3.3 s (budget 1 s; plain 16 ms). Keeping one handle per file per process, with the layout in memory, brought it to about 0.35 s with `synchronous=normal` and 0.49 s with `synchronous=full`; the rest is the syncs a rollback journal needs. `full` was kept.
- `VACUUM INTO 'file:...?vfs=…'` from a plain connection writes through the named VFS, and a sealed connection's `VACUUM INTO` a plain path goes through the sealed VFS too (the target takes the connection's VFS): a backup's working folder must be given the keys. The output is a rollback-journal database (header bytes 18 and 19 are 1), so a plain write-ahead-log database copies into one the VFS can open.
- `cmd/keystone`'s test served its folder with the `file` keeper, and with a plain person in it the first test run sealed that person under a master key file in the user's profile. The test now passes a keeper held in memory (`openAPIWith`).
- The keeper takes `in.mu`, which `Install.Store` held while it opened a person: the keys are unwrapped before the lock is taken, and `Create` seals after `createPlain` returns.

## Questions, each with a recommended answer

1. **The backups made before sealing stay until someone deletes them.** Each holds everything the person had, sealed under a passphrase only this install can unwrap. Recommended: the owner deletes `data/backups/before-encryption` after a week of using the encrypted install, as the runbook says. Built: nothing deletes them.
2. **One process at a time opens a sealed person.** A command (`tenant secret set`, `tenant backup`) waits up to 30 seconds while the server has that person open, and is then refused. Recommended: keep it; a command is short and the server opens a person per request. If it bites, raise `encryption.lock_wait`. Built: as recommended.
3. **`tools/tenant add` makes a plain person** (the command does not read `encryption.at_rest`), sealed at the server's next start with a backup. Recommended: leave it; the server does not see a person added from the command line until it starts again anyway (decision 0641). Built: as recommended.
